# 功能点标注模板库（开放式 / v1.0）

> ## 🧭 核心定位（北极星 — 一切标注规则的出发点）
>
> **标注 = 用户在原型上「框住某个位置」，AI 用「用户的语言」输出该功能区域的「字段规范」+「用例规则」。**
>
> - **框住位置**：一个区域 / 字段 / 状态页签 / 按钮 / 列表 / 详情，皆可框选。
> - **用户的语言**：业务与操作视角（"用户点这里 → 看到什么 → 触发什么"），**绝不写后端技术实现**（调接口 / 写库 / 拉数据）。
> - **输出两样**：① **字段规范**（这块有哪些字段、各字段属性与约束）；② **用例规则**（用户在这块怎么用）。
>
> **价值（为什么做这个工具）**：框选即出 PRD 内容——**画原型与写 PRD 一体化**，PM 不再"画完原型还要手写一遍 PRD"。原型即 PRD 的可视化入口，标注内容直接沉淀为 PRD 文档。
>
> **🎯 北极星适用两个输入通道，输出同质（铁律）**：无论从哪个通道圈定位置，AI 都必须按该位置的**真实业务场景**输出「字段规范 + 用例规则」，格式与质量完全一致，绝不输出"功能区 / 按实际业务补充"这类与内容无关的空壳。
> - **通道②（原型内点/框）**：用户在原型上右键点元素 / 画框框区域 → 原型内 `genAnnoDraft` 用框内真实文字（`zoneTexts`）生成草稿。**点与框行为必须一致**（点击路径 `_detectZone` 必须同样采集 `zoneTexts`，否则点击会因无上下文退回空壳）。数字指标卡片（仪表盘"标签+数值"）必须识别为只读统计指标。
>   - **区域取名铁律（绝不取按钮）**：画框框选时，区域名**只取框内的"卡片/区域标题"**（class 含 `title` 或 `h1~h4`、卡片头部标题），**所有按钮一律排除在取名之外**。框整块区域 = 该区域的功能 PRD（如框「账户余额」整块，即便内含「充值」按钮，也命名并生成"账户余额"区域 PRD）；**只有右键单击按钮本身**，才生成该按钮的功能 PRD（如单点「充值」才出充值 PRD）。框 1 张卡=该卡名；框 2~3 张=标题并列；框整盘多卡=区域概览（如"数据看板"），**禁止被框内恰好包含的单个功能点（按钮）劫持**。`genAnnoDraft` 里"按名字模糊匹配功能点"对多数值+多标签的统计区要跳过，避免被劫持。
>   - **⚡ 圈选采集完整性铁律（2026-06-27 加 · 根治"采集漏数据"一整类）**：框只要【碰到】一个逻辑区（状态条 `.stabs` / 消息tab / EP-tab `.el-tabs__nav` / 带 `data-annotation-zone` 的区），就取该区【**全部**】同级标题/字段，**绝不要求每个元素像素级落在方框内**——否则方框差几像素就漏掉末个页签（实测：状态少"已驳回"，且 OMS/WMS 不一致）。**原则：客户端只"完整搬运"不"猜"；圈一个区 = 取该区完整内容（名称 / 字段 / 枚举全集，禁截断）**；此原则同样约束 `zoneTexts` 字段采集与 `zoneHTML`（禁因框没罩全 / 截断而丢内容）。代码落点：`annotation-layer.html` 框选取名段以 `_ZONE_SEL` 命中区 → `z.contains` 补齐该区全部同级标题（标准件 + 注入的每个原型同步）。同源地，`zoneTexts` 字段采集也并入 `_zoneSet` 全部叶子文本（状态/枚举全集不漏）；`zoneHTML` 采集上限 4000→40000（表单/筛选区/表格等真实区域完整不切，仅病态超大留安全网，实测筛选区 8846/表格 8163 字符旧上限会丢约 4-5K）。
>   - **🌐 单一真理源·无缝继承（一句话铁律）**：以上全部圈选采集铁律只写在标准件 `annotation-layer.html`，PM 画新原型、客户打包安装后用任何 AI 工具（OpenClaw/Cursor/Claude/Codex/Hermes）都自动继承、无缝使用、达到完全一样的效果——标准件改一处，所有原型一致，绝不逐原型修补。
>   - **⚡ 名字与身份解耦铁律（2026-06-28 加 · 改名不串内容）**：复制给 AI 对话框的每条 = **名字(纯标签)** + **身份id**（有绑定用 fpKey / 无绑定用稳定 `zoneId`）+ **原型真实内容**（`zoneTexts` 字段/状态/枚举全集）。**AI 必须按 id + 内容生成，绝不照名字猜**；用户改名（变长短/好看）只动标签，**绝不改变要生成的范围与内容**。代码落点：`_copyFnList` 每行输出 `名字 / 身份id / 原型真实内容`；`RULE_HEADER` 写死"名字仅显示标签"。验证方式：node 确定性测试（改名后 id/内容一字不变）+ Playwright 真机（框故意切掉末个页签，区完整逻辑仍补回完整 4 状态，旧逻辑掉 1 个）。
>   - **🎯 错配彻底根治：精确绑定 OR 真实内容，绝不模糊猜（结构性铁律 / 商业级必守）**：错配（同名 / 跨视图 / 跨页）的**唯一根源**是"按名字猜功能点"。彻底方案 = 两条合起来，让猜错在结构上不可能：
>     1. **精确绑定优先**：原型给每个功能点元素打 `data-annotation="<fp_key>"`。框/点命中带此属性的元素 → **直接用该 fp_key 取真实字段/用例**（框选 `card.querySelector('[data-annotation]')` 单卡片单绑定才用；点击 `target.closest('[data-annotation]')`；传 `genAnnoDraft(boundFp)`）。如**首页余额展示卡**(`账户余额-OMS.首页右侧顶部`) vs **账户余额列表查询页**(`账户余额-OMS.查询`) 同名，靠 data-annotation 精确区分。
>     2. **取消名称模糊匹配**：无精确绑定时，**禁止 `_matchPrdFp` 之类按名字相似度去匹配某个 fp**（`prdMatch` 只认 `boundFp` 精确命中，否则 `null`）。改用框内**真实 zoneTexts/zoneGroups** 描述屏幕真实有的字段，或标"待 AI 生成"。
>     → 结果：草稿**要么精确绑定、要么如实描述真实内容、要么待 AI 生成，永不输出"猜错的某功能点内容"**。这是商业级 agent 必须做到的——外部用户看到错内容会投诉。配合 [[multi-view-same-name]]。
>     （前置纪律：生成原型时**每个功能点元素必须打 data-annotation**，生成后自检覆盖率——见 prd-data-schema §8。）
>   - **点 / 框两种交互（行为规范）**：
>     - **点模式**：右键单击具体元素（按钮/图标/状态页签/列标题）→ 弹气泡 →【确定添加】→ 采集该元素真实上下文（`zoneTexts` 叶子文字 + `zoneHTML` 元素 DOM 片段）+ 生成 PIN + 入队（状态"待生成"）。
>     - **框模式**：右键区域空白处 → 进画框模式 → 拖拽框住 → 松开 → 弹气泡（区域名按上条"取名铁律"只取卡片标题）→【确定添加】→ 采集**分板块字段 `zoneGroups`** + 区域 HTML + 生成 PIN + 入队。
>   - **采集即入队（关键机制）**：每个 PIN 必须把真实上下文存进 `pin.zoneContext = { zoneGroups, zoneTexts, zoneHTML }`；【让AI更新PRD】把所有 PIN（含 `zoneContext`）打包写入 `anno-queue.json`（本地服务在跑时自动发送，否则降级剪贴板）。
>   - **生成流水线（达到通道①质量）**：AI 工具收到队列后，**读 `zoneContext` 真实上下文**按本北极星**重新生成**——多卡片按板块分组列字段、用例讲清各板块能看到什么/能做什么——**禁抄 PIN 里的 JS 草稿**（草稿仅离线占位/参考）→ 三步同步回写。**点 / 框 / 对话框① 三者输出质量完全同质。**
>   - **🔁 AI草稿自愈架构（商业级必守铁律）**：`genAnnoDraft` 在浏览器内启发式生成的草稿内容**随时可能因代码改进而过期**；不得依赖一次写入永久正确。必须实现以下三件事，缺一不可：
>     1. **`isAIDraft` 标记**：`genAnnoDraft` 输出的 PIN 必须设 `isAIDraft: true`；用户在面板保存编辑后清除为 `false`（用户确认的内容不被覆盖）。
>     2. **自动刷新**：原型初始化时调用 `_refreshStaleDraftPins()`，对所有 `isAIDraft === true` 的 PIN 用 `pin.zoneContext` + 最新 `genAnnoDraft` 重新生成内容——**代码每次改进后，所有未确认草稿 PIN 下次刷新浏览器自动更新**，不需要用户手动删 PIN 重建。
>     3. **模板继承**：以上两条必须写进 `annotation-layer.html` 模板——任何新原型注入标注层时，自动获得自愈能力，不需要逐原型修补。
>     → 违反此铁律的后果：genAnnoDraft 某分支写了错误模板词（如"近30天/时间维度/骨架屏"），会永久留在用户 localStorage；只能手动删 PIN 才能修复——在商业客户环境中不可接受。
>     → 对应代码约定：`genAnnoDraft(zoneId, zoneLabel, zoneTexts, zoneGroups, boundFp, zoneHTML)` 第 6 参数 `zoneHTML` 必须显式传入（不得依赖闭包隐式读取，否则无法在 refresh 时复现）；KPI数字卡片（`!hasRealChart`）与折线/柱状/饼图（`hasRealChart`）必须走不同分支，禁止用相同图表模板。
> - **通道①（对话框驱动，含两种子模式，能力 ≥ 通道②）**：AI 自动分析所指位置的**业务规则 + 场景 + 行业标准规范**，输出**同样格式**的字段规范（行业基线+业务规则双层）+ 用例规则（7 节），并执行 **PRD 三步同步铁律**（写 `prd-data.json` → PRD `.md` → 回写原型 `window.__PRD_DATA__`）。
>   - **①-A 纯描述（无截图）**：用户说"首页那个区域 / APP 某页 / 网站某区域 要生成 PRD" → AI 按下方"数据来源优先级"取真实内容并生成。
>   - **①-B 有截图**：用户贴截图（在图上标了位置，或只说"截图里某区域"）→ AI 读图识别该区域真实字段/控件后生成。
> - **数据来源优先级（决定 PRD 质量，高→低）**：① 用户当前截图/明确参考 → ② 原型 `window.__PRD_DATA__` / `prd-data.json`（该区域已存在则读真实字段，单一真理源）→ ③ 原型 HTML 实际渲染 → ④ 行业标准基线 + 业务对象常识（该区域尚不存在时按行业规范推断）。
> - **推断必确认（铁律）**：当来源落到③/④（凭描述或截图推断 UI 结构/字段/必填）时，AI 必须先把推断结果 + 不确定点列给用户确认，再落库（遵守 [[confirm-screenshot-inferences]]）；来源①/②（有真实数据）可直接生成。
> - 两通道**彼此独立、可自由切换**（见 v1-master-spec §1.6）；**绝不允许只有②能做、①做不到**。
> - **🔧 工具无关 + 禁抄草稿（铁律 / 面向插件分发）**：本能力**不绑定任何特定 AI 工具**——用户用 **OpenClaw / Cursor / Claude / Codex** 等任一 AI 代理装上本插件后，行为必须完全一致（不得出现"只有 Claude 能做"的假设）。**任何 AI 工具**收到标注/队列（如用户点「让AI更新PRD」、或在对话框说"生成PRD"）时，**必须读取该区域的真实上下文**（原型 HTML 实际渲染 / `window.__PRD_DATA__` / `prd-data.json` / 框选采集的 `zoneGroups`）**重新生成**字段规范与用例；**严禁直接照抄通道②在浏览器里出的 JS 启发式草稿**——那只是离线瞬时占位，权威内容必须由 AI（用户所用的任一代理）读真实数据按本规范生成。`anno-server` 仅作"浏览器↔文件"的桥（落成 `anno-queue.json`，任何 AI 代理都能读），不含智能、不绑定工具。
>

## 消息通知格式铁律（强制 / 单一真理源） {#消息通知格式铁律-强制-单一真理源}

> **本节是「消息通知」节的唯一格式真理源。**任何通道（对话框① / 原型②）、任何 AI 工具生成「消息通知」节时，**有通知必须严格按本节的 Markdown 4 列表格输出**，禁止退回纯文字散文（如"系统通知财务审核人员审核"这类写法一律不合格）。对应强制条款 §38。

### 1. 标准 4 列表格模板（有通知时必用）

```markdown
| 通知场景 | 通知标题 | 通知内容 | 接收方 |
|---|---|---|---|
| <触发该通知的业务动作/状态> | <通知卡片标题，简短> | <通知正文，动态字段用 {占位符}> | <具体接收方角色> |
```

- **必须三行齐全**：表头行 `| 通知场景 | 通知标题 | 通知内容 | 接收方 |` + 分隔行 `|---|---|---|---|` + 至少一条数据行。
- 一个功能点触发多类通知（如审核「通过/驳回」两种结果）时，**每类各占一数据行**。

### 2. 占位符规则（通知内容里的动态字段）

- 通知内容里凡是运行时才确定的字段，一律用 `{占位符}` 包裹，**不写死示例值**。
- 常见占位符：`{申请人}`、`{提交时间}`、`{审核时间}`、`{审核人}`、`{充值金额}`、`{币种}`、`{驳回原因}`、`{单据编号}` 等；按功能点真实字段命名，与字段规范里的字段名保持一致。

### 3. 业务下发类操作必有消息通知（接收方必须具体）

凡是会影响他人/下游角色的业务下发动作，**必须写消息通知表格**，不得写「无。」：

- 提交（如充值申请提交）、审核（通过/驳回）、出库、付款、收款、上架、下架、发货、签收、退货、调拨、放款、还款、开票等。
- 接收方**必须是具体角色**（如「财务审核人员」「门店店长」「采购员」「申请人」），**严禁写"操作人 / 发起人 / 相关人员"**这类泛指。
- 业务下发 8 类必双消息的更细规则见 §9 与 _rules §4.6.4；§9 的 `双消息` JSON 结构与本节表格等价，PRD 渲染时统一展示为本节 4 列表格。

### 4. 无通知功能点写「无。」

- 查询 / 查看 / 筛选 / 重置 / 导出（无下游接收方时）等只读或自助类功能点，消息通知节固定写 `无。`（一个汉字句号），不写占位文字，不写空表格。

### 5. 真实示例（充值管理 — 供照格式套用）

**充值申请提交 → 通知财务审核人员：**

```markdown
| 通知场景 | 通知标题 | 通知内容 | 接收方 |
|---|---|---|---|
| 充值申请提交 | 有新充值申请待审核 | 客户 {申请人} 于 {提交时间} 提交了充值申请（申请金额：{充值金额} {币种}），请尽快审核。 | 财务审核人员 |
```

**充值申请审核（通过/驳回）→ 通知充值申请人（两行各一类结果）：**

```markdown
| 通知场景 | 通知标题 | 通知内容 | 接收方 |
|---|---|---|---|
| 充值申请审核通过 | 您的充值申请已通过 | 您于 {提交时间} 提交的充值申请（金额：{充值金额} {币种}）已于 {审核时间} 审核通过，余额已到账。 | 充值申请人 |
| 充值申请被驳回 | 您的充值申请被驳回 | 您于 {提交时间} 提交的充值申请（金额：{充值金额} {币种}）于 {审核时间} 被驳回，原因：{驳回原因}。请修改后重新提交。 | 充值申请人 |
```

> **写法落地**：在 prd-data.json 的 `_draft_useCaseRules` / 各功能点 `message_notifications` 中，有通知时直接存上述 Markdown 表格文本（含表头+分隔行+数据行）；无通知存 `"无。"`。anno-server 渲染 PRD §4.x 时原样输出，`_notifRows(fpKey)` 必须能解析该表格（见 §32）。

## §34 anno-server 自动生成 PRD 铁律（强制）

> anno-server 运行中时，PRD 文件生成由 server.js 全自动处理，AI **无需**介入文件写操作。

### §34.1 立即响应
- 收到 `/anno-update` 或 `/anno-inject` 请求后，**同步处理**，在响应返回前完成所有文件写操作
- 不允许异步延迟、不允许批处理队列，用户点击后必须立即感受到反馈

### §34.2 数据驱动 §1-§4.3（高质量，非通用模板）
- PRD §1-§4.3 必须基于 `prd-data.json` 中的真实数据生成，绝不使用"XXX系统""某功能"等占位符
- 检测逻辑：
  - 扫描所有 `fpKey` 提取系统标识（WMS/OMS/APP/H5/B2B/B2C 等）
  - 根据检测到的系统生成对应的术语定义（WMS：入库/出库/波次；OMS：订单/履约/逆向等）
  - §4.3 业务流程图按实际系统类型生成（WMS：收货→上架→拣货→发货；OMS：下单→履约→配送→签收）
- `prd-data.json` 不存在时：从同目录原型 HTML 的 `window.__PRD_DATA__` 用大括号计数法提取初始化

### §34.3 用户编辑内容绝对优先
- `mergePinIntoPrd()` 必须**无条件**将 `pin.fieldSpecs` 写入 `_draft_fieldSpecs`、`pin.useCaseRules` 写入 `_draft_useCaseRules`
- 禁止任何 `hasStructured` 类判断阻止草稿覆盖
- `buildFpSections()` 中 `_draft_fieldSpecs` 优先级高于 `field_specs.groups`；只要草稿存在，结构化数据不展示

### §34.4 pandoc 静默跳过
- pandoc 不可用（未安装/命令失败）时，静默跳过 .docx 生成，不中断流程，不报错给用户
- .md 文件仍必须正常生成

### §34.5 fpKey 解析规范
```
格式：<模块名>[-<系统标识>].<功能点名>
示例：充值管理-WMS.充值 → { module: "充值管理", system: "WMS", fp: "充值" }
示例：充值管理.充值   → { module: "充值管理", system: "",    fp: "充值" }
系统标识（大小写不敏感）：WMS / OMS / APP / H5 / PC / B2B / B2C / ADMIN
```

## §35 预览模式（?preview=1）铁律（强制）

> 原型分享给客户时，必须在 URL 末尾加 `?preview=1`，严格限制客户只能查看，不能操作。

### §35.1 五项严格禁止（preview=1 时必须隐藏/禁用）
1. **顶部「生成研发PRD」按钮**：`v-if="!isPreviewMode"` 隐藏整个按钮
2. **标注弹窗底部操作按钮**：删除、编辑、生成 PRD 等按钮全部 `v-if="!isPreviewMode"` 隐藏
3. **AI 命令栏**：`v-if="pinModeOn && !isPreviewMode"` 整个命令栏隐藏
4. **_showTrigger 触发器**：函数第一行加 `if (isPreviewMode) return;`，禁止右键弹出新建标注气泡
5. **字段规范/用例规则输入框**：CSS `pointer-events:none; background:#f7f8fa; color:#888` 禁止编辑；添加行 `display:none`

### §35.2 两项必须保留
1. **标注开关**：客户可以自由开/关标注显示，这是唯一保留的交互
2. **「👁 预览模式」指示器**：顶部右侧显示小字提示，让客户知道当前是只读模式

### §35.3 实现方式（组件固定写法）
```javascript
// ④ Vue setup 开头处
const isPreviewMode = new URLSearchParams(location.search).get('preview') === '1';
if (isPreviewMode) document.body.classList.add('anno-preview-mode');
```

body.anno-preview-mode .cel-select,
body.anno-preview-mode .uc-sec-ta,
body.anno-preview-mode .fs-group-lbl input { pointer-events:none !important; background:#f7f8fa !important; color:#888 !important; }

body.anno-preview-mode .uc-add-row,

## §36 双向同步两条通道（强制架构）

> 两条通道技术完全独立，结果等价，可自由混用，任一方故障可切换到另一方。

### §36.1 通道②：原型操作 → 文件自动生成
```
用户右键标注 / 点「生成研发PRD」
  → POST /anno-update { changes:[{zoneContext:{fpKey}, title, fieldSpecs, useCaseRules}] }
  → anno-server：
      ① 合并写入 prd-data.json（_draft_fieldSpecs / _draft_useCaseRules）
      ② 生成 PRD-*.md（§1-§4.3 数据驱动 + §4.4 功能点明细）
      ③ pandoc → PRD-*.docx（不可用时静默跳过）
      ④ 更新原型 HTML window.__PRD_DATA__（大括号计数法定位边界）
  → SSE broadcast prd-updated → 原型 toast 提示（不 reload）
```

### §36.2 通道①：AI 对话框 → 文件生成 + 原型实时同步
```
用户在对话框说「给 X 功能加标注」
  → AI 生成 fieldSpecs + useCaseRules
  → POST /anno-inject { pins:[{fpKey, title, fieldSpecs, useCaseRules, menuPath?}], systemName? }
  → anno-server：同上 ①②③④ 四步
  → SSE broadcast inject-pins { pins }
  → 浏览器原型 window._annoInjectPins(pins) 被调用
      - 按 fpKey 查找现有 PIN → 更新内容
      - 未找到 → 用 [data-fp-key] / [data-annotation-key] / 文字搜索定位 DOM 元素
      - 在元素位置 createPin(..., fieldSpecs, useCaseRules, ..., isAIDraft=true)
      - _savePins(); showPins.value = true; ElMessage.success(...)
  → 原型实时显示新标注 PIN（无需刷新页面）
```

### §36.3 两通道混用规则
- 用通道①在对话框生成的标注，会自动显示在原型上并写入本地文件
- 用通道②在原型上编辑的内容（`isAIDraft=false`），下次触发时以用户编辑版为准
- 用通道①重新生成某功能 PRD 前，若用户已在原型上编辑过，AI 应先询问是否覆盖

## §37 AI 对话框注入标注 5 步操作规范（强制）

> AI 收到「给 X 功能生成 PRD 标注」类指令时，必须严格按以下 5 步执行。

**Step 1：确认 fpKey 格式**
- 从用户描述提取：模块名 + 系统标识（可选）+ 功能点名
- 格式：`<模块名>[-<系统标识>].<功能点名>`，例：`充值管理-WMS.充值`
- 不确定时主动询问，不猜测

**Step 2：生成高质量标注内容**
- `fieldSpecs`：按 §3 对应 fp_type 模板生成字段规范，双层规则（行业基线 + 业务特定，见 §31）
- `useCaseRules`：生成 3-6 条业务规则，覆盖正常流 + 边界 + 异常
- 内容必须基于用户描述和已知业务上下文，不输出通用占位符

**Step 3：调用 /anno-inject**
```json
POST http://localhost:3799/anno-inject
{
  "pins": [{
    "fpKey": "<模块名[-系统].功能点>",
    "title": "<功能点显示名>",
    "fieldSpecs": "<生成的字段规范文本>",
    "useCaseRules": "<生成的用例规则文本>",
    "menuPath": "<可选，菜单路径>"
  }],
  "systemName": "<可选，产品系统名>"
}
```

**Step 4：anno-server 处理（自动，无需 AI 介入）**
- server.js 完成 prd-data.json 写入 + PRD.md/.docx 生成 + HTML 回写 + SSE 广播
- AI 等待 HTTP 响应（同步）

**Step 5：告知用户结果**
```
✅ 已为「<功能点名>」生成标注并注入原型
✅ 原型浏览器中已实时显示新标注 PIN（无需刷新）
✅ prd-data.json 已更新 → PRD-*.md / .docx 已生成
```
- 若 anno-server 未运行（连接失败）：提示「anno-server 未启动，请先启动后再执行注入」，不静默失败

## §38 字段类型库（16 类预设字段，快速插入标准约束）

> **核心价值**：同一系统内金额/手机号等通用字段在多个功能点里约束必须一致。字段类型库提供行业标准基线约束，PM 点击芯片即插入，再叠加业务特定规则，杜绝"充值金额、提现金额、对账金额各写一套"的不一致问题。

### §38.1 16 类预设类型（标准约束，AI 必须与组件保持一致）

| 类型名 | 字段类型 | 标准约束基线 |
|---|---|---|
| 手机号 | 字符串 | 11位；以1开头；支持+86前缀；不含空格 |
| 金额 | Decimal | ≥0.01；最多2位小数；上限999,999,999.99 |
| 身份证号 | 字符串 | 18位；前17位数字末位可为X；校验码验证 |
| 日期 | Date | 格式YYYY-MM-DD；不可选未来日期（如有限制须注明） |
| 日期范围 | DateRange | 开始日期≤结束日期；最大跨度90天（可配置） |
| 银行卡号 | 字符串 | 16-19位纯数字；Luhn算法校验 |
| 邮箱 | 字符串 | 含@和域名；最大254字符；符合RFC5322 |
| 密码 | 字符串（加密存储） | 8-20位；须含大小写字母和数字；不存明文 |
| 企业名称 | 字符串 | 2-100字符；不含<>&等特殊字符 |
| 数量 | Integer | 正整数；最小值1；最大值（请填写上限） |
| 百分比 | Decimal | 0-100；最多2位小数；单位% |
| 状态 | 枚举 | 可选值：（请填写）；不可为空；默认值：（请填写） |
| 备注 | 字符串 | 最大500字符；可为空；前端超长时截断并提示 |
| 文件 | File | 格式：（请填写）；大小上限：（请填写）MB |
| 统一社会信用代码 | 字符串 | 18位；格式校验（数字+大写字母组合） |
| IP地址 | 字符串 | IPv4格式x.x.x.x；各段0-255 |

### §38.2 AI 使用规范（通道①注入时强制）

AI 在通道①（对话框注入）生成字段规范时，对于匹配上述 16 类的字段，必须：
1. **先套用标准约束基线**（行业基线，见上表）
2. **再叠加业务特定规则**（如金额：`≥0.01；最多2位小数；上限999,999,999.99；单次≥100元；当日≤500,000元`）
3. **禁止只写业务规则**（如只写"≥100元"而不写精度/上限），否则研发要猜基础约束
4. 这是 §31 双层规则的具体落地：**第一层=上表标准基线；第二层=当前业务特定规则**

### §38.3 PM 使用路径（原型内）

```
点开 PIN → 编辑 → 字段规范 Tab → 顶部芯片行（16 个类型按钮）
   ↓
点击类型名（如「金额」）→ 字段表格自动新增一行，约束已按上表填好
   ↓
在约束列末尾追加业务特定规则
   ↓
点【生成研发PRD】→ anno-server 自动生成
```

## §39 AI 遗漏扫描（/anno-scan 端点）

> **核心价值**：PM 圈完标注后无法知道"还有哪些功能没标"——人无法感知自己不知道的事。遗漏扫描由 anno-server 扫描原型 HTML，与已有 PIN 对比，把未标注的业务功能元素列出来，PM 决定哪些补标。

### §39.1 技术规范

- **端点**：`GET http://localhost:3799/anno-scan`
- **触发路径**：PM 点 PIN 详情 → 右上角【🔍 扫描遗漏】按钮
- **返回格式**：`{ ok: true, items: [{text: "批量导出"}, ...], scanned: N }`
- **扫描范围**：`archive/` 目录下所有 `原型-*.html` 文件
- **过滤逻辑**：只返回有业务含义的元素（过滤"确认/取消/关闭/保存/刷新/导出/搜索/查询/重置"等纯 UI 操作）；匹配业务关键词（新增/充值/审核/提现/申请/结算/开票等）；与 prd-data.json 现有 fp_name 对比去重；最多返回 20 条

### §39.2 AI 行为规范

- anno-server 未运行时：弹错误提示「anno-server 未启动，无法扫描」，不静默失败
- AI **无需介入扫描过程**——扫描由 anno-server 自动执行，AI 在此功能里的角色是帮 PM 对扫描结果里的条目补充标注内容
- 若 PM 把扫描结果条目发给 AI 说"帮我标注这几个"→ AI 按 §37 五步流程执行，fpKey 从条目文字+模块上下文推断

### §39.3 PM 决策规则（AI 不替 PM 决定）

扫描结果是候选，不是必须全部补标：
- PM 点【+ 添加】→ 系统在原型里对应元素旁创建 PIN，PM 再补内容
- PM 不点 → 表示本次不纳入 PRD 范围（不是遗漏，是主动决策）
- anno-server 判断"已有标注"的依据：prd-data.json 里 fp_name 与元素文字完全匹配

## §40 用户反馈→PRD（客户原始反馈直接转 PRD 变更）

> **核心价值**：客户需求散落在企微/钉钉/邮件/工单里，传统流程 PM 要先理解反馈、再找到对应 PIN、再手动改字段规范。此功能把三步变一步：PM 粘入原始反馈 → AI 自动识别 fpKey + 变更内容 → 调用 /anno-inject 一次写入。

### §40.1 PM 操作路径

```
底部 AI 命令栏 → 点【📋 反馈】→ 粘入原始反馈（企微/钉钉/邮件/工单原文）
   ↓
点【复制给 AI 处理】→ 系统将反馈 + 结构化提示词一起复制到剪贴板
   ↓
切换到 AI 工具（Ctrl+V 粘贴）→ AI 分析处理
   ↓
AI 识别 fpKey → 调用 /anno-inject → 原型 PIN 实时更新 + PRD 文件同步生成
```

### §40.2 AI 执行规范（收到反馈转 PRD 指令时必须按此执行）

**Step 1：识别 fpKey（不猜，要推断+确认）**
- 从反馈文字里提取业务实体（如"充值金额"→ 充值管理.充值）
- 结合已知菜单结构（从原型 HTML 或 prd-data.json 读取）确认 fpKey
- 若反馈涉及多个功能点（如"充值最低改10元，另外导出要加操作人"）→ 拆成多个 fpKey 分别处理

**Step 2：判断变更类型**

| 反馈特征 | 变更类型 | 操作 |
|---|---|---|
| "最低/最高/改成/限制" 等约束词 | 修改字段约束 | 找对应字段行，改约束列内容 |
| "加一个/需要有/显示" 等新增词 | 新增字段 | 在 fieldSpecs 追加新字段行 |
| "必填/选填/可以不填" 等属性词 | 修改字段属性 | 找对应字段行，改必填列 |
| "如果/当/驳回时" 等条件词 | 新增/修改用例规则 | 在 useCaseRules 追加或修改对应规则 |

**Step 3：调用 /anno-inject**（格式同 §37 Step 3）
- `fieldSpecs` / `useCaseRules` 只传有变更的 fpKey，不传全量（避免覆盖其他 PIN 内容）
- 若 anno-server 未运行：提示用户启动 anno-server 后重试，不降级为手动改文件

**Step 4：告知变更摘要**
```
✅ 已根据反馈更新以下标注：
  • [fpKey 功能点名] — [具体变更说明，如：充值金额最小值改为10元]
  • [fpKey 功能点名] — [具体变更说明，如：导出字段新增「操作人」「操作时间」]
✅ 原型 PIN 已实时更新（无需刷新）
✅ PRD-*.md / .docx 已同步生成
```

### §40.3 适用场景（AI 主动识别触发）

| 用户说的话 | AI 应该做的 |
|---|---|
| 「客户反馈 XX，帮我更新 PRD」 | 直接走 §40.2 流程 |
| 粘入原始聊天记录/工单 + 「更新标注」| 识别其中的需求变更，走 §40.2 |
| 「把这条反馈加进 PRD」 | 同上 |
| 「刚开完需求评审，研发说 XX 要补 YY」| 同上，研发反馈 = 用户反馈 |

> 🏛 **铁律**：无论反馈来源（客户/销售/测试/研发），原文粘入即可，AI 负责识别变更点，PM 不需要先"翻译"成结构化格式。
