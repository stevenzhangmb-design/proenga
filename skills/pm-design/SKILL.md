## 🏛 工作原则：以用户参考为准 + 发现问题主动提醒（v1.0 强制）

> ⚠️ **核心铁律**：用户提供的参考（截图 / 链接 / 已学过的设计样本 / 实际系统截图）= **最高优先级真理源**，AI 必须按用户参考画原型，**不能用自己的想法武断覆盖**。但如果发现参考有问题，AI **必须主动提醒用户**，由用户决定是否改。

> 🔒🔒 **UED 行为铁律（最高优先 · 任何 UI / 布局 / 控件改动都适用 · 根治"AI 自作主张做反人类设计、不自检就交付"）**：
> 1. **严格按选定规范执行，不自行优化 UED**：默认按 system-design-spec.md / 用户给的参考做；**即使你觉得"按最佳 UED 应当改善 / 调整"、有合理建议——也必须先提给用户、用户决定后再改**（默认规范、学竞品 都一样）。建议须建立在【行业最高 UED 标准 + 最好用户体验】上，不随手拍。
> 2. **交付前必自己【截图】视觉自检，禁自我感觉良好**：凡改动界面位置 / 布局 / 浮层 / 控件摆放，交付前**必用无头浏览器 / CDP 截图亲眼看**——有没有遮挡关键控件（尤其开关 / 关闭 / 提交 / 返回）？关键操作还够得着吗？菜单多的系统会不会挤 / 错位？任意系统都成立吗？**「元素在不在」≠「好不好用」；断言要验"用户能不能真用"。**
> 3. **浮层（`position:fixed` 覆盖）默认怀疑**——先问"它盖住了什么？"；优先把控件**内联进头部**，不做覆盖式浮层。
> 违反任一条 = 反人类设计 / 糊弄交付，禁止。（2026-06-25 用户因 AI 把工具条做成浮层盖住「标注」开关、且没截图自检就交付，立此强制铁律。）

### 🏛🔒 原型合规闸（机器闸 · 交付前必跑 · 随包发 · 根治"不遵循 pm-design 画原型"）

> 🏛 **铁律（不靠 AI 自觉，靠机器闸兜底）**：每**生成/修改一个原型 HTML，交付给用户前必须跑** `qa/prototype-pmdesign-gate.js`；**红（exit 1）= 不合规，禁交付**——必须按 pm-design 重画后跑到绿才能交付。
>
> 命令：`node skills/pm-design/qa/prototype-pmdesign-gate.js <原型.html | 目录>`
>
> 检查项（缺一即红）：**C1** 已整段原样注入 `components/annotation-layer.html`（标注层，否则圈选/框选→PRD 断链）· **C2** `window.__PRD_DATA__`（单一真理源）· **C3** Element Plus · **C4** `data-annotation` / `ak()` 标注锚点 · **C5** Vue 运行时 · **C6** 渲染器/顶栏从 [page-renderer](./components/page-renderer.html) + [host-shell](./components/host-shell.html) 原样装配（跑 `qa/renderer-contract-gate.js` 全绿 · 禁手搓漂移）。（含 `__ANNO_READONLY__=true` 的只读分享版豁免 C4。）
>
> **为什么**：曾出现 AI 画"裸 HTML 原型、无标注层"导致用户无法圈选生成 PRD（违反 Phase 2 + prd 铁律 R-D）。靠 AI 自觉会漏；此闸**随包发**，任何 AI 工具 / 任何打包后的用户生成原型都被强制约束，不合规当场红、禁交付。

> 🏛🔒🔒 **效果一致性三条铁律（最高原则 · 2026-06-30 用户立 · 根治"标注层注了但开关失效/工具条不显示"）**：
> 任何原型都必须达到"标注层真正可用"的完整效果（顶栏标注工具条显示、开关能开/关、右键能圈选→对话框生成 PRD），适用于以下全部情形，无一例外：
> 1. **我**在任意对话框（N 个新对话框 / 现有对话框）画新原型时；
> 2. **打包后**，别人在其他 AI 工具安装、使用时；
> 3. **打包后**，别人在其他 AI 工具的任意对话框（N 个新 / 已有）画新原型时。
>
> **怎么保证（不靠自觉）**：
> - **正路是组件装配、不手搓**：顶栏/标注工具条须从 [host-shell.html](./components/host-shell.html) + [page-renderer.html](./components/page-renderer.html) 原样装配（标注开关/复制已圈功能/导出分享版/清空 已接通 `window.__anno`）；手搓极易漏接桥接导致开关失效。
> - **闸已强化为"验真能用"**（`qa/prototype-pmdesign-gate.js`，**检查项以闸文件为准、本处不枚举**，以免新增 C9/C10 后文字过期）：核心是「宿主头部标注控件接桥 `window.__anno` + 视图同步 + `data-annotation` 锚点充足 + 卡片标签可识别」等；只"整段粘贴标注层"而不在宿主头部接通控件即判红、禁交付。
> - **闸已挂 Stop 自动钩子 + 写入随包 `.claude/settings.json.example`** → 谁画的原型不达标都被自动拦、随包对所有安装用户生效。

### 优先级层次（从高到低）

1. **用户当前对话给出的参考**（截图 / URL / "按 X 系统的样子做"）— **最高**
2. **用户之前让 AI 学过的样本**（[learned-specs/](./learned-specs/) 下的文件 / 之前发的截图）— **高**
3. **PRD 铁律 + 标注层 UI 规范 + 原型业务流程规范**（_rules / schema §8）— **必守底线**
4. **团队默认规范**（[system-design-spec.md](./system-design-spec.md)）— **兜底**
5. **AI 自己的想法 / 公共最佳实践** — **最低，仅作辅助参考**

### AI 接到画原型任务的必走流程

```
1. 识别用户提供的参考来源
   ├ 截图？→ 仔细看截图，按截图布局/样式/字段/控件画
   ├ 链接？→ 抓取后按链接的样式画
   ├ "学过的 XX"？→ 读 learned-specs/<slug>.md 按它画
   └ 都没有？→ 用团队默认规范

2. 把参考转换为原型代码（按参考为准）

3. 发现参考与规范冲突时（如：截图里没有面包屑，但规范要求 B 端必须有面包屑）：
   ├ ❌ 不要默默改成符合规范的样子
   ├ ✅ 在生成原型前/后，主动提醒：
   │   "我注意到 [截图里 XX] 与 [规范 YY] 不一致，
   │    可能的处理：
   │    A. 按你的截图做（保留 XX）
   │    B. 按规范改（改为 YY，理由：...）
   │    你倾向哪个？"
   └ 等用户决定后再继续

4. 不要凭空臆造参考里没有的内容
   ├ 截图里有 6 个字段 → 原型 6 个字段
   ├ 截图里没出现的字段 → 不要自动加
   └ 字段名 / 控件类型 / 必填标识 必须按截图

5. 截图模糊不清的地方 → 主动问，禁臆造

6. 【拷贝真实系统/竞品·完整性铁律】用户让"完整拷贝/搬过来/参照现有系统"某页面时，必须**一列不漏、一个页签不漏、每个下钻详情都抓**：
   ├ **多页签报表**：逐个点开每个 tab（如 按日期/按客户/按商品、仓库/客户/商品），每个页签列往往不同，都要抓
   ├ **虚拟表格(ag-Grid: .ag-header-cell / .ag-header-row)**：列是虚拟渲染的，**只截可见区永远漏列**——必须**横向滚动 .ag-body-horizontal-scroll-viewport 逐段收集全部列**（按 col-id 去重）；el-table 用 `th .cell` 能一次抓全
   ├ 有"操作/查看"列或可点(蓝色)单元格 → **点进去把详情页/弹窗也抓了**（列+数据）
   ├ 抓完先**自查列数**、交付前**浏览器验列数对得上真实系统**，禁"抓到几列就当抓完"
   └ 骨架支持：多页签用 statusTabs（每 tab 挂自己的 columns/rows/filters/actions）；可点单元格用 `data-act` 触发弹窗
   （2026-08-02 用户震怒：让完整拷贝行业标杆WMS 报表，AI 只抓可见 11 列交付、实为 19 列，立此铁律。详见记忆 feedback_copy_system_completely_no_truncation）
```

### 持续学习用户提供的所有参考

- 用户每次发截图 / 链接 → AI 都应该问"是否要存到 learned-specs/ 作为以后参考？"
- 用户说"按 X 系统的风格" → AI 应该先检查 learned-specs/ 里有没有 X
- 用户说"参考之前那张截图" → AI 应该能找到（如果之前存过）

### 发现问题主动提醒的标准句式

```
"我注意到 [参考来源的具体位置 / 内容]，可能有以下问题：
 - [具体问题 1]
 - [具体问题 2]
 建议处理：
 A. 完全按你的参考做（保留原样）
 B. 我建议改成 [具体建议]，理由：[规范依据 / 用户体验考量]
 你倾向哪个？"
```

**禁止做法**：
- ❌ 看到截图里的问题默默"修正"成自己认为对的样子
- ❌ 不读用户的参考就开始按团队规范画
- ❌ 看到参考与规范冲突时不提醒，自己擅自决定
- ❌ 凭空臆造参考里不存在的字段 / 控件 / 区块

**正确做法**：
- ✅ 优先读用户参考，按参考画
- ✅ 发现冲突 → 主动提醒 → 让用户决定
- ✅ 参考模糊处 → 主动问，不臆造
- ✅ 持续把用户的参考存进 learned-specs/ 作为后续工作的资产

### 🏛 改一处必扫全局同类 → 报告 → 用户决策 → 再改（v1.0 强制 / 2026-06-21 用户明确要求）

> 🏛 **核心铁律 / 适用所有交付物**：用户指出某个问题（如"明细表的会计期间没标题，和汇总表不一致"）让 AI 改时，**绝不允许只改用户指的那一处就完事**。**不论改的是原型 HTML、PRD、技术设计、测试用例、操作手册、售前方案，还是设计规范本身**，AI 都必须：
> 1. **先改用户指出的那一处**；
> 2. **立刻把整份交付物（整个原型 / 整篇 PRD / 整个文档）扫一遍，找出所有"同类问题"**（同一种控件/字段/组件/交互/术语/表述/口径在别处是否也有同样毛病——尤其跨模块、跨地区版本 CN/BR、跨汇总/明细/详情/弹窗、跨章节）；
> 3. **在对话框里把发现的同类问题列成清单**（位置 + 问题 + 建议），**交给用户决策**——而不是默默全改，也不是只改一处不管别处；
> 4. **用户决定改哪些后，再统一改**。

**为什么**：用户多次反馈"你太死板，改一个地方就只改一个地方，要智能一点"。一个不一致几乎从不孤立存在——同样的控件/范式/术语往往在多个模块、两个地区版本、多个章节里重复，只改一处会留下一堆同病。**原型和 PRD（及其他文档）都会有这类情况**。但**也不能擅自全改**（用户要保留决策权、避免过度改动）。所以是"主动扫描 + 报告 + 用户拍板"。

**标准动作**：
```
（改完用户指的那处后）
"已改 [用户指出的位置]。我顺手扫了整份[原型/PRD/文档]，发现同类问题还有：
 | 位置 | 问题 | 建议 |
 | ... | ... | ... |
 这些要一起改吗？（全改 / 只改哪几个 / 不改）你定，我再动手。"
```

**禁止做法**：
- ❌ 用户指一处、AI 改一处，对明显的同类问题视而不见
- ❌ 不问就把扫到的同类问题全部擅自改掉（剥夺用户决策权）
- ❌ 扫描只看当前模块/当前章节，漏掉另一个地区版本（CN/BR）、汇总/明细/详情/弹窗、或文档其他章节的对应位置

> **适用范围（不限于原型）**：原型——列名、字段口径、组件范式、交互方式、文案措辞、控件标题等；PRD / 技术设计 / 测试用例 / 手册 / 售前方案——字段定义、术语叫法、表述口径、章节结构、命名规范等。凡"应当一致"的东西被改动，都走"改一处 → 扫全文 → 报告 → 用户决策 → 再改"。

## 🗺️ 完整工作流（5 阶段 / 适用所有产品形态）

> 本工具覆盖 PM + 研发 + 测试 + 运营全链路，PM 流程是第一阶段。

### Phase 1：画原型

1. PM 描述需求（竞品截图 / 现有系统 / 直接说功能）
2. AI 生成原型 HTML，存至用户指定输出目录（默认 `./archive/`）
3. PM 在浏览器打开，核对 → 说"标题改 / 加一列" → AI 增量改
4. 反复直到 PM 说「原型 OK」

### Phase 2：圈定 PRD 范围

> **核心定义**：PRD 不是对整个原型的全量描述，而是 PM 主动圈定的「这次交付研发评审的功能范围清单」。不在清单里的功能不出现在 PRD 里。

**方式①（对话框）**：说「给充值按钮、筛选区、操作列生成 PRD」→ AI 读原型 HTML 自动识别字段/操作/状态，PM 不需要逐字段描述

**方式②（原型内右键）**：开「标注」开关，按目标类型走不同路径：
- **单个元素**（按钮/操作列图标/状态页签/列标题字段）→ **直接右键单击** → 弹确认气泡 → 点「确定添加」
- **区域/大块**（搜索区/表格行/表单等）→ **右键单击空白处**进入画框模式（光标变十字）→ **左键拖拽**框住区域 → **松开** → 弹确认气泡 → 点「确定添加」（再次右键或 Escape 取消画框模式）

两种方式可混用，结果合并到同一份 `prd-data.json`。

### Phase 3：编辑标注内容

**方式①（标注页直接操作）**：点开标注 pin → 编辑字段规范 / 用例规则 / 删除 pin

**方式②（对话框）**：直接告诉 AI，例如：
- 「把充值按钮的字段规范里，充值金额改为最小100元」
- 「筛选区的用例规则增加：日期范围最长支持90天」
- 「删除导出按钮的标注，这个功能不写PRD」

> ⚠️ **数据安全**：标注改动存浏览器 localStorage —— 关浏览器/关电脑不丢，但换设备/清缓存会丢。**改完必须触发 Phase 4 才算真正存档。**

### Phase 3 辅助功能（v2.1 新增，标注层内置）

**🏷 字段类型库（快速插入标准约束）**

点开 PIN → 编辑 → 字段规范 Tab → 顶部芯片行，共 16 类（手机号/金额/身份证号/日期/日期范围/银行卡号/邮箱/密码/企业名称/数量/百分比/状态/备注/文件/统一社会信用代码/IP地址）。点击类型名 → 字段表格自动插入带标准约束的行 → PM 在末尾追加业务特定规则。

解决问题：同一系统内金额/手机号等字段在多个功能点里约束不一致，研发不知道哪个算数。AI 在通道①注入时也必须按 §38 的标准基线生成约束，不能只写业务规则。详见 [annotation-templates.md §38](./annotation-templates.md)。

---

**🔍 AI 遗漏扫描（发现未标注的功能元素）**

完成一轮标注后 → 点开任意 PIN → 右上角【🔍 扫描遗漏】→ anno-server 扫描原型里所有有业务含义的按钮/页签，与已有 PIN 对比 → 右侧面板列出未标注条目 → PM 逐条点【+ 添加】或忽略。

- anno-server 必须运行中（`GET http://localhost:3799/anno-scan`）
- 解决问题：PM 圈完以为做完了，评审时研发才发现缺某些功能点的规则。详见 [annotation-templates.md §39](./annotation-templates.md)。

---

**📋 用户反馈→PRD（客户原始反馈直接转 PRD 变更）**

底部 AI 命令栏 → 点【📋 反馈】→ 粘入企微/钉钉/邮件原始反馈 → 点【复制给 AI 处理】→ 切到 AI 工具粘贴 → AI 自动识别 fpKey + 变更类型 → 调用 `/anno-inject` → 原型 PIN 实时更新 + PRD 文件同步生成。

- AI 收到"帮我把这条反馈更新到 PRD"类指令时，按 [annotation-templates.md §40](./annotation-templates.md) 流程执行
- 解决问题：客户需求散落在聊天/邮件里，PM 要手动找 PIN → 定位 Tab → 逐行改；此功能把三步变一步。

### Phase 4：生成研发 PRD（每次改完都要做）

**PM 侧三种触发方式，任选其一：**

| 方式 | 操作 |
|---|---|
| **标注页底部** | 打开任意标注详情 → 底部「生成研发PRD/更新PRD」（改完随手点）|
| **顶部按钮** | 导航栏右侧「让AI更新PRD」（徽章数字 = 未同步条数）|
| **对话框** | 告诉 AI「帮我生成研发PRD / 更新PRD」|

触发后：原型把所有标注（**含真实上下文 `zoneContext`**）发到本地服务 `anno-server`（localhost:3799）落成 `anno-queue.json`；服务未启动则降级复制到剪贴板，由用户粘贴给 AI。

#### 🏛 AI 端队列处理流程（任何 AI 工具必须照做 / 工具无关 / 这是"②达到①质量"的关键）

> 触发条件：检测到 `anno-queue.json` 有未处理内容，**或**用户粘贴了原型生成的"北极星指令"。任一 AI 工具（OpenClaw/Cursor/Claude/Codex）都按下列步骤执行，行为一致。

1. **逐条读真实上下文**：取每条标注的 `zoneContext = { zoneGroups, zoneTexts, zoneHTML }` + 原型 `window.__PRD_DATA__`/`prd-data.json`，作为真实业务数据。
2. **按来源优先级 + 北极星生成**（见 annotation-templates 北极星）：
   - **新增类**：基于真实上下文**重新生成**高质量字段规范（多卡片**按板块分组**、不扁平；数字看板=只读统计指标、异常红色、待处理可下钻）+ 用例规则（讲清用户在各板块**能看到什么/能做什么**）。**严禁照抄队列里的 JS 草稿**（草稿仅占位/参考）。
   - **编辑类**：用户已手改的，**以用户改动为权威**，仅做同步搬运，不重新生成覆盖（见 [[annotation-never-blocks-business]] 同源的用户优先铁律）。
   - **推断必确认**：原型尚无该区域、只能靠 zoneHTML/描述推断时，先列推断 + 不确定点给用户确认再落库。
3. **二次自检（对抗校验 / 落库前强制）**：内容生成后、落库前，重读该条 `zoneContext`（`zoneHTML` 真实 DOM / `zoneGroups` / `fpKey`），逐项核对——① 有没有编造屏幕上不存在的字段？② 视图对不对（OMS 内容里不得出现 WMS/"全部客户"，反之亦然）？③ 跟 `zoneHTML` 真实内容一致吗？④ 精确绑定 `fpKey` 命中时，内容是否就是该 fp？任一不一致 → 自我修正后再落库，禁止带着不一致直接写文件。
4. **三步同步回写**（缺一不可）：① 更新 `prd-data.json`（单一真理源）→ ② 生成/更新 `PRD-XXX-日期.md` + pandoc 转 `.docx`（存用户输出目录）→ ③ 回写原型 `window.__PRD_DATA__`。
5. **清空队列**：处理完把 `anno-queue.json` 清空（或标记已处理），避免重复生成。

→ **点/框/对话框三通道经此流程后质量完全同质**；文件不依赖浏览器/设备，任何电脑任何时候都能打开。

AI 完成后汇报：
```
✅ PRD 已更新：§X.Y 功能名（共 N 条标注）
✅ prd-data.json 已同步 · PRD-XXX-日期.docx 已生成
✅ 原型 window.__PRD_DATA__ 已回写 → 刷新浏览器即可看到最新标注
```

### Phase 5：核对 & 修改

- PM 查看 `.docx` 文件
- 说「§X.Y 改成…」→ AI 同时完成：更新 `.md`、重新生成 `.docx`、回写原型 `window.__PRD_DATA__`
- 确认后 → 提交研发评审

### Mode 0：学习设计规范（不画原型）

| 维度 | 内容 |

| **输入** | 三种之一：① 公开网站 URL（如 `linear.app`）② 公开设计系统站（如 `polaris.shopify.com`）③ 私有系统 / App 截图（3-5 张关键页：首页 / 列表 / 表单 / 弹窗）|
| **AI 处理** | ① 抓取 / 识图 → ② 提取设计 token（颜色 / 字体 / 间距 / 圆角 / 阴影 / 组件库识别）→ ③ 整理为统一 spec 格式 → ④ 存到 [learned-specs/](./learned-specs/) 下，文件名 `<slug>.md` |

| **后续** | 后续 Mode 1 / 2.2 画原型时，用户可指定 `用 learned-specs/<slug>.md 画一个 XX 页面` |

**Mode 0 三种输入源详解**：

| 源类型 | 例子 | 提取方式 | 完整度 |
|---|---|---|---|
| ✅ **公开网站** | `linear.app` / `stripe.com` / `notion.so` | WebFetch HTML/CSS + 截图分析视觉 | 高 |
| ✅✅ **公开设计系统站** | `polaris.shopify.com` / `m3.material.io` / `ant.design` | 直接抓官方 token 文档 | 极高（最准）|
| ⚠️ **私有系统 / App** | 公司内部 ERP / iOS App | 用户拖 3-5 张截图 → AI 识图 | 中（取决于截图质量与覆盖度）|

**Mode 0 已知限制**（AI 必须在产出时告知用户）：
1. 复杂动效 / 微交互 → 抓不到（CSS 静态可抓，动画有限）
2. 登录态私有系统 → 必须截图，无法登录抓
3. iOS / Android 原生 App → 100% 靠截图，无 URL
4. 整站设计系统 → 单页好抓，全套规范要多次抓
5. 反爬 → 部分网站可能拒绝抓取，遇到则要求用户改用截图

### 🏛 Capture Mode 的 3 种实际工作方式（v1.0 / 用户不写提示词）

> 🏛 **核心铁律**：用户**从来不写提示词、不给字段骨架**。全部由 AI 反推/出方案 → 用户核对 → 用户说改 → AI 增量改 → 定稿。

**方式 1：竞品反推融合**
- 触发：用户拖竞品截图/链接 + 在对话框说 "在竞品基础上**加 X 减 Y**"
- AI 必须：**融合竞品参考 + 用户增减需求** → 反推提示词

**方式 2：现有系统增量改造**
- 触发：用户拖现有系统截图 + 改动描述 "在 X 处加 Y"
- AI 必须：**主动给新功能的排版布局方案**（不只是识别现有）

**方式 3：AI 主动出方案**
- 触发：用户**不知道怎么做** + 没竞品 + 没现有系统 + 只说模糊需求
- AI 必须：**扮演资深 PM**，主动出业务架构方案（菜单/字段/流程/状态机/角色）
- ❌ 不能反问"你想做什么样的"（用户就是不知道才问 AI）

**方式 4：文档分析 + 系统建议（两阶段 / 乙方接项目场景）**
- 触发：用户发文档（客户需求文件 / 产品大纲 / RFP / 招标文件 / 会议纪要 / 长文本）
- 支持格式：Word / PDF / Excel / Markdown / 邮件正文 / 对话框长文本
- AI 必须走**两阶段**：
  - **阶段 A 业务咨询**：扮演**资深产品架构师 + 业务顾问**，按 [business-analysis-template.md](./business-analysis-template.md) 输出 `./archive/业务分析-XXX-<日期>.md`（8 章节：业务分析 / 系统类型建议 / 核心模块 / MVP 划分 / 技术栈 / 风险点 / 待澄清问题 / 下一步建议）
  - **阶段 B 出原型**：用户说"按方案 X 出原型" → 转 Capture Mode 方式 3 出原型
- ❌ 不能直接出原型（必须先咨询，用户决定方向后再画）
- 典型场景：乙方接客户项目 / 投标售前 / 新业务调研 / 会议纪要落地

### 🏛 菜单结构是 PRD 命脉

用户不写提示词，但 AI 反推 .md 必须有 **§A0 菜单结构** 独立章节让用户核对。
- 菜单结构 → PRD §4 章节编号
- 菜单改（加/删/改名）→ AI 同步 3 处：① 原型侧栏+面包屑 ② prd-data.json menus ③ PRD §4 章节自动重排

### 🏛 画原型前必先问：四问弹窗（v1.0 强制 / **每次都问** / 2026-07-05 由单问扩为三问 · 2026-07-10 增第④问语言）

> 🏛 **铁律**：**每次**用户让 AI 画原型（Mode 1 / 2.2），AI **动手前必须先用 AskUserQuestion 弹窗让用户逐项决策**——四件事：**① UI 规范　② 端/形态　③ 地区/币种/时区　④ 支持哪些语言**。**无论有没有拖竞品**、**禁止**擅自直接套默认开画（2026-06-08 用户要求）。**① UI 规范这一问原样保留、绝不丢**（旧版就问它）。

**提问方式**：优先用 AskUserQuestion 弹窗（四个 question 一次弹）；无法弹窗时用**人话**把四项发给用户（**禁倒 system-design-spec / WMS 栈 / UTC 等机器术语**，见下方话术）。

**① UI 设计规范**（明细见下方「决策对照」A/B/C 表）：
```
A. 默认规范（从真实生产代码提炼·2026-07-07·旧的作废）—— 直接落地。选 A = UI 按②的形态走 system-design-spec.md（B端）或 system-design-spec-mobile.md（移动版）。
B. 我来提供（竞品/网址/设计稿/规范文档/文字描述任一）—— 缺失按行业标准补全不反问
C. 用之前学过的 learned-specs/<某个>.md
```
> 🏛 **技术栈不在画原型问**：画原型只定 UI（+②端+③地区）。**前后端技术栈在点【导出研发版】时才确认**——提示"确认采用默认技术方案吗？" → 是则按 `_shared/dev-stack-spec.md` 出料；否则用户先发技术栈给 AI 学习（存 learned-stack）再导出。画原型阶段用不上技术栈，不问、不逼。完整流程见 [`../_shared/acceptance-checklist.md`](../_shared/acceptance-checklist.md) 附则 A。

> 🏛 **画原型五条防坑铁律（强制·任何 AI 工具都照办）**
> 1. **必走四问**（① UI 规范 ② 端/形态 ③ 地区/币种/时区 ④ 语言）——装配器靠这四答烙 `__DESIGN_CHOICE__`，闸靠它验一致。
> 2. **必须用标准装配器（模式1 `assemble-prototype.js`），禁手搓单文件**。手搓原型没有 `__PRD_DATA__`/`__DESIGN_CHOICE__`/标准件，会**静默逃逸全部机器闸**，且**将来导不了研发版**（拿不到料）——发票那个手搓版就是前车之鉴（`function_points: {}` 空、标注跨页飘移）。
> 3. **PRD 必须填全**（字段规范 + 7 节用例规则）。**这是导出研发版的命门**：PRD 糙 → 料糙 → 生成的代码照样烂（garbage in, garbage out）。
> 4. **画完 + 生成 PRD 后必跑 `qa/deliver-gate.js` 全绿**再交付（涉 UI 改动另需截图眼验）。
> 5. **禁擅自改 `system-design-spec.md` / `system-design-spec-mobile.md` / `dev-stack-spec.md`**（默认规范三件套）。多对话框并行时，两边同改一个源文件会**互相覆盖**；要改先确认由谁独占。

> 🏛 **【圈选后 PIN 是空的 —— 这是设计，不是 bug】（B 架构·2026-06-23 用户拍板 · 强制）**
> - **圈选/点选 = 只圈范围。** 客户端**绝不生成任何 PRD 内容**，新建的 PIN 里 `fieldSpecs` / `useCaseRules` **就是空的**，显示"待生成"。
> - **PRD 内容唯一来源** = 点【复制已圈功能】→ 粘到 AI 对话框 → AI 按 `prd` skill 规则**真推理**生成 → `/anno-inject` → 回填 PIN + 落 `prd-data.json`。
> - ⛔ **看到"圈完没内容"不要去"修"它。** 历史：客户端曾内嵌 650 行启发式模板猜内容 → 质量差、拆东墙补西墙、根本跑不通（用户多天实测判死），已于 2026-07-09 整段删除。
> - ⛔ **禁止在客户端重新实现 `genAnnoDraft` 去猜内容**——`qa/anno-fix-guard.js` 的静态断言 ⑥⑦ 会立刻判红（⑥ 必须直接返回空内容；⑦ 层内不得出现 7 节模板文本）。

**② 做给哪种端（形态）**（也影响原型长相，故开画前问；技术栈细节见 archive「默认技术栈参考-B端与移动版」）：

| 选项 | 默认技术栈 | 说明 |

| **B 端后台** | WMS 栈（Vue3+TS+Vue CLI+Vuex+Element Plus+自研 i18n+Jest/Cypress） | 桌面表格/筛选/批量操作 |
| **网站** | 暂未定（待补·可能 Vite 那套） | 官网/商城前台·面向 C 端访客 |
| **移动版（APP/小程序/PDA）** | PDA 栈（uni-app+Vue3+JS+uv-ui+uni.$uv.http+扫码） | 触屏/rpx·一套码发 App/小程序/H5/PDA |

> **①②联动·设计规范按形态各走各的**（选 A 默认规范时）：选 **B 端后台** → 走 [`system-design-spec.md`](./system-design-spec.md)（EP + px 桌面版）；选 **移动版** → 走 [`system-design-spec-mobile.md`](./system-design-spec-mobile.md)（uv-ui + rpx + 扫码，主色 #3363FF 与 B 端一致）。派子 agent 做 UI 时，指令里必须点名让它**先读对应那份规范**再动手。

**③ 地区 / 币种 / 时区**：

| 模式 | 选项 | 效果 |
|---|---|---|
| **单地区固定** | 中国（¥/UTC+8/YYYY-MM-DD）· 巴西（R$/UTC−3/DD-MM-YYYY） | 币种/时区**写死** |

**④ 支持哪些语言**（2026-07-10 用户要求新增·**必问，禁默认单语开画**）：

| 选项 | `locales` | 说明 |
|---|---|---|
| **单语中文** | `["zh"]` | 语言切换器**不渲染**。文案可写普通字符串。 |
| **中/英/葡（推荐）** | `["zh","en","pt"]` | 顶栏出语言切换器。**默认显示中文**（`defaultLocale:"zh"`），演示给巴西客户时切 `pt`。 |

- **切/不切的判据 = "UI 词汇 还是 数据实例"**（不是"在不在表格里"）：
  - ✅ 切：**枚举值**（状态标签 `已开票/待开票`、类型 `销售发票/采购发票`）—— 真实系统里也走 i18n。状态标签写 `{"t":{"zh":…,"en":…,"pt":…},"c":"green"}`。
  - ❌ 不切：**数据实例**（单号 `NF-000128`、日期、金额、客户名、商品名）—— 真实系统里存在库里。
- **`region=BR` + 多语 → `locales` 必须含 `pt`**，否则 ㉝闸判红。
- 机制、切换范围、EP 内置文案覆盖 → 见 [`system-design-spec.md`](./system-design-spec.md) §5.5。

> 🏛 **圈选 / PRD 一律以中文为准**：开启标注自动切回中文并提示；标注开启期间语言锁定。
> 原因：标注层采集的是**当前 DOM 上显示的文字**，葡语下圈选会把 `fp_name` 写成 `Lista de NF`，同一功能还会被圈成两个 PIN。骨架已强制，无需 AI 额外处理。

> **默认出口**：用户说"都默认" → **默认 UI 规范 ＋ B 端后台 ＋ 中国区 ＋ 单语中文**，并显式告知用了哪套默认。**技术栈不在此问**——点【导出研发版】时确认"默认技术方案吗？"（是→按 dev-stack-spec 出料；否→先发技术栈给 AI 学习再导）。任一项说"其他/换 X" → 按用户说的来。
> **完整规格**：archive「画原型开场-默认选择提醒-详细清单」（含币种/时区对代码范式的影响·选多币种多时区必遵）。

> 🏛 **四问答案必落 `__DESIGN_CHOICE__`（强制·供自动自检）**：问齐四项后，**把答案作为 `choice` 传给装配器**（`assemble-prototype.js` 会烙成 `window.__DESIGN_CHOICE__ = {ui, form, region, currency, timezone, locales, defaultLocale}`）；自带骨架/手搓时也必须手写这行。画完后 Stop 钩子的 **㉝ 选择一致性闸**自动验"原型 == 所选"（币种/前端栈/语言声明漂移即红），**㉟ 三语完整性闸**验缺译。**自定义 UI** 另加 `__DESIGN_SPEC_CUSTOM__` 标记豁免默认令牌。
> 🏛 **画完必回显选择（防听错·一句话）**：原型/PRD 出炉后，用一句话回显所选让用户当场核对，例：「✅ 已按〔默认UI · B端后台 · 巴西 R$ · America/Sao_Paulo · 中/英/葡（默认中文）〕生成」。闸防"画着画着漂移"、回显防"一开始就听错"，两者合起来才完整。

### 🏛 PRD 范围定义：PM 主动圈定，双入口并存（v1.0 / 适用所有产品形态）

> **核心定义**：PRD 不是对整个原型的全量描述，而是 PM 主动圈定的「这次交付研发评审的功能范围清单」。
> APP / 网站 / 所有 B 端系统都是同一逻辑：不是所有区域都要写用例，只有 PM 明确圈入的才进 PRD。
> **画框只是圈定方式之一，对话框也是方式之一，两种并存，产出完全一样。**

#### 三种标注触发方式（可混用，产出合并到同一份 prd-data.json）

| | 方式①：对话框说功能名 | 方式②：原型内右键 | 方式③：截图+指位置 |
|---|---|---|---|
| 操作 | 说"给充值按钮、筛选区生成标注" | 开标注开关 → **右键单个元素直接弹气泡** / **右键空白区进入画框模式→左键拖拽** | 发截图 + "标注左上角这个区域" |
| 触发时机 | 知道功能名的时候 | 在浏览器里直接操作 | 截任何图都能用，含竞品截图 |
| AI 行为 | 自动扫描 HTML 识别该区域真实字段 | 识别右键目标元素或框内 UI 元素 | 识别截图里的 UI 元素，映射到原型 HTML |
| 产出 | 字段规范 + 用例规则 → pin → prd-data.json | 同左 | 同左 |
| 可混用 | ✅ | ✅ | ✅ |

#### 方式① 执行协议（AI 行为规范，每次必须按此执行）

**Step 1 — 解析意图，提取功能区列表**

从用户说的话中提取要标注的功能区，支持任意自然语言表达：
- 「给充值按钮生成标注」→ `[充值按钮]`
- 「标注筛选区和操作列」→ `[筛选区, 操作列]`
- 「把整个充值管理页面都标注」→ 自动识别页面所有主要功能区

**Step 2 — 自动扫描 HTML 真实字段（禁止靠猜）**

对每个功能区，从原型 HTML 里读取真实内容：
- 表头/表单标签 → 字段名
- 按钮文字/操作图标 → 操作项
- 状态 Tab/状态列 → 状态值
- 角色差异操作 → 权限相关

PM 只需说"圈哪个区域"，AI 负责从 HTML 读字段，**不凭空臆造字段**。

**Step 3 — 并行生成（功能区 ≥ 2 个时）**

多个功能区同时分析、同时生成内容，不串行等待。

**Step 4 — 内容质量自检（Rule24-27，写入前必过）**

- Rule24：识别功能类型（展示类/操作类/跳转类）→ 套对应模板
- Rule25：用例规则**全文**必须用用户语言，禁止出现：异步任务/接口调用/写入数据库/（详见术语：xxx）/API/后端/消息队列等任何技术用词
- Rule26：展示类字段规范去掉"必填/选填"→ 改为"只读"
- Rule27：展示类操作日志 → 固定为"查询/查看不输出操作日志"

**Step 5 — 增量注入，不覆盖已有标注**

只更新本次指定的功能区 pin，其他已有标注完整保留。
在 prd-data.json 每个 pin 写入 `injectedAt` 时间戳（ISO 格式）。

**Step 6 — 结构化反馈（固定格式，每次必输出）**

```
✅ 已注入 X 个标注 pin：
  • [功能区名] — X个字段规范 / X条用例规则
  • [功能区名] — X个字段规范 / X条用例规则
🔧 自动修正 X 处：（Rule26：展示类字段去掉"必填" × X / Rule27：操作日志修正 × X）
刷新浏览器即可查看
```
若无自动修正，🔧 行省略。

#### 方式② 执行协议（原型内右键标注 — PM 操作流程，精确版）

> 这是 PM 在浏览器里直接操作的可视化标注流程。右键行为根据目标自动分叉，PM 无需记规则，右键点什么就标什么。

**场景 A：标注单个元素（直接右键，最快）**

适用于：按钮、操作列图标（查看/编辑/删除/审核）、状态页签、列标题字段

1. 右上角开启「标注」开关（蓝色）
2. **直接右键单击**目标元素（按钮 / 操作图标 / 页签 / 列标题）
3. 立即弹出确认气泡「是否为「XXX」生成 PRD？」
4. 点「确定添加」→ 系统生成字段规范 + 用例规则
5. 标注 pin 落在元素上，带编号方块（如 ⑦）
6. 点击编号方块 → 弹窗查看/编辑内容

**场景 B：标注区域（右键空白→画框，用于搜索区/表格/表单等大块）**

适用于：搜索筛选区、列表整体、表单分块、页面区域

1. 右上角开启「标注」开关
2. **右键单击目标区域的空白处**（非按钮/图标/页签）→ 出现提示「✏️ 画框模式 — 左键拖拽框住区域，再次右键取消」，光标变为十字 `✛`
3. **按住左键不松** → 拖拽框住目标区域（出现蓝色虚线选框）
4. **松开左键** → 弹出确认气泡「是否为「XXX 功能区」生成 PRD？」
5. 点「确定添加」→ 系统识别框内 UI 元素，生成字段规范 + 用例规则
6. 标注 pin 落在框中心，带编号方块
7. **再次右键** 或 按 **Escape** 可随时取消画框模式

> **铁律**：右键命中的是"点"（按钮/图标/字段标题）→ 直接出气泡；右键命中的是"面"（行/区域/容器空白）→ 进画框模式。两条路自动判断，PM 不需要手动切换。

**两种场景共用的后续步骤**

- 点击任意标注 pin 编号 → 查看字段规范 + 用例规则（默认查看态）
- 点「编辑」→ 可修改任意节内容，改完自动保存
- 点「让AI更新PRD」→ 变更同步到 prd-data.json 和原型 HTML

#### 方式③ 执行协议（截图驱动）

1. 识别截图里的 UI 元素：按钮名、字段名、区域布局、操作项
2. 在原型 HTML 里按文字内容匹配对应元素
3. 生成并注入标注（同方式① Step 4-6）
4. **竞品截图特殊处理**：识别竞品字段后，映射到我们原型的对应区域，生成符合我们 PRD 规范的标注内容

> 方式③不需要任何额外开发，是 AI 原生多模态能力，现在就能用。

#### 范围清单累积 = 提交研发的 PRD

```
PM 用方式① 说："给充值按钮、筛选区写标注"      → 加入清单
PM 用方式② 框住：操作列（查看/审核/驳回）        → 加入清单
PM 用方式③ 发截图："标注这个状态页签区域"         → 加入清单
                          ↓
                这份清单 = 提交研发评审的 PRD
```

**不在清单里的功能区，不出现在 PRD 里** — PM 的主动决策，不是遗漏。

#### Step 5 AI 标准句式

```
"原型 OK！现在定一下这次 PRD 的范围——你想给研发哪些功能写字段规范和用例规则？

方式①（直接说）：对话框告诉我，如"给充值按钮、筛选区、操作列写标注"
方式②（原型内右键）：右键单个元素（按钮/图标/页签/列标题）→ 直接弹气泡；右键区域空白处 → 画框模式 → 左键拖拽框住区域 → 松开
方式③（截图）：  截图发给我，告诉我"标注哪个区域"，我来识别

三种方式可以混用，结果合并到同一份 PRD。
你来定范围，AI 只生成你圈定的部分，不会自动全量生成。"
```

⚠️ **禁止**："按这个画" 后一次性出原型+PRD；必须分步等用户每个 Quality Gate 确认。

### 🏛 增量同步铁律

用户改某一处 → AI **只更新 3 处**（原型 HTML / prd-data.json / PRD .md 对应段），**不全文重写**，不动无关内容。详见 [prd-data-schema.md §8.7.9.5](./prd-data-schema.md)。

> 🏛 **核心价值**：用户给竞品截图 / 链接后，AI **不直接画原型**，而是先输出一份"我理解的画原型提示词"让用户核对。核对通过后再触发 Mode 1 / 2.2 画。**避免 AI 误判用户意图，节省返工成本**。

| 维度 | 内容 |
|---|---|
| **触发** | 见 [模板 §0](./prototype-prd-prompt-template.md) 的 4 种场景识别 |
| **输入** | 截图 / 链接 / learned-specs / 用户提示词 / 用户文字描述（4 种场景对应 4 种输入组合） |
| **AI 处理** | ① 场景识别 → ② 按对应填充策略填模板 §1-§9 → ③ §10 标出不确定点 → ④ §∞ 加场景扩展节 → ⑤ 输出 `.md` 让用户核对 |
| **输出** | `./archive/画原型+写PRD提示词-<名称>-<YYYY-MM-DD>.md`（基于统一模板）|
| **后续** | 用户核对 → 修改 / 确认 → 用户说"按这个画" → 触发 pm-design Mode 1/2.2 出原型 + prd skill 出 PRD |

## 🤝 多需求并行调度（Multi-Agent / 工具无关）

> AI 作为主调度者，将需求拆解后派发给多个子 Agent。**是否开启并行由用户决定**，默认顺序执行。

### 触发方式

**默认：顺序执行**（一个完成后再做下一个，方便随时插入修改）
> 「帮我做三件事：①画充值管理原型 ②生成账户余额PRD ③画流水记录原型」

**主动开启并行**：在需求里加「同时」「并行」「一起」等关键词
> 「**同时**帮我做三件事：①画充值管理原型 ②生成账户余额PRD ③画流水记录原型」

### 调度模型

```
PM（一句话描述多个需求）
    ↓
主 AI（拆解 + 调度）
    ├── 子任务 1 → 充值管理原型
    ├── 子任务 2 → 账户余额 PRD        ← 并行执行，互不等待
    └── 子任务 3 → 流水记录原型
    ↓ 全部完成
汇总结果给 PM
```

### 可并行 vs 不可并行

| 场景 | 是否可并行 | 原因 |
|---|---|---|
| 多个不同模块的原型 | ✅ | 各自独立 HTML 文件，无冲突 |
| 多个模块的 PRD 文档 | ✅ | 各自独立 .md/.docx 文件 |
| 原型生成 + 上个模块测试用例 | ✅ | 操作不同文件 |
| 两个任务同时修改**同一个** HTML | ❌ | 会互相覆盖 |
| 两个任务同时写**同一个** PRD 文件 | ❌ | 内容冲突 |

### 各 AI 工具的实现方式

| AI 工具 | 并行调度实现 |
|---|---|
| **Claude Code** | 内置 Agent 工具 / Workflow 工具，原生支持并行 |
| **OpenClaw（SkillHub）** | 腾讯云 Hy3 模型驱动；支持多 Agent 并行调用，使用 OpenClaw 自身的 Agent 机制执行本 skill |
| **Cursor** | Background Agent 模式，支持多 Agent 并行 |
| **Codex（OpenAI）** | 原生多 Agent 支持，并行执行多任务 |
| **其他 AI 工具** | 按各工具自身的 Agent 机制执行，支持多 Agent 则并行，否则顺序执行 |

> **跨工具原则**：本 skill 描述的是调度**意图和规则**，具体执行机制由各 AI 工具自行决定。逻辑不变，机制因工具而异。

## 🤖 模式自动识别规则（AI 行为铁律）

按以下顺序判断：

```
0. 用户内容是否含 ① URL（含网站 / 系统地址）② "学一下 X 的设计" / "参考 X 的设计规范" / "把 X 的设计语言抓出来"
   ③ App 名 + "学/抓/吸收/提取" ？
   YES → Mode 0（学习设计规范，不画原型）
   NO  → 进 3a

3a. 用户内容是否含 ① 竞品截图 + "按这个画" / "参考这个" / "做一个类似的"
   ② 竞品链接 + "做一个像这样的" ③ "按 learned-specs/X 的样式做一个 Y"
   YES → Capture Mode（反推画原型提示词，不直接画，等用户核对）
   NO  → 进 1

1. 用户内容是否含"系统视图与角色"+"菜单结构与功能点"？
   YES → 检查是否有截图
        无截图 → Mode 1（全新模块）
        有截图 → 询问用户："是要参考截图设计新模块？还是基于截图改造？"
   NO  → 进 2

2. 用户内容是否含"现有模块菜单路径"+"改动描述"？
   YES → 检查是否有截图
        无截图 → 改走 prd skill 场景 A（PRD-only 文字增量）
        有截图 → Mode 2.2（截图增量画原型）
   NO  → 进 3

3. 都不符合 → 用户输入不清晰，主动询问：
   "请补充：① 是想学某个外部设计规范？② 是新模块还是改现有？③ 有无现有截图？"
```

**Mode 0 与其它 Mode 共存关系**：
- Mode 0 是"输入规范"动作；Mode 1/2.x 是"输出原型"动作
- 用户可先 Mode 0 学规范 → 再 Mode 1 用学到的规范画原型（典型流程）
- 用户也可只走 Mode 0（仅想学规范留档，暂不画）或只走 Mode 1/2.x（用团队默认规范，不学新的）

### 🏛 画原型铁律（最高 · 标准部件三件装配 · 禁手搓 / 根治漂移）

> **新对话画原型，照本条办即可达到"本地最新效果"——文件存哪、谁来画都无关。**

**【默认·首选】画原型 = 跑装配器，不手写 HTML。** AI 只产出一份**纯 JSON 项目数据**（schema 见 [examples/project-data.sample.json](./examples/project-data.sample.json)：systems/home/nav/pagecfg；rows 为二维数组、标签单元写 `{"t":"文本","c":"green"}`，禁任何函数调用），然后：
```
node qa/assemble-prototype.js <project-data.json> <输出原型.html>
```
装配器从 [components/prototype-skeleton.html](./components/prototype-skeleton.html)（结构唯一源·标准部件全固定）+ annotation-layer.html **逐字复制**产出原型——**标准部件不经 AI 的手 → 手搓出错结构上不可能**。产出后跑 `qa/prototype-pmdesign-gate.js`（C1–C9）+ 浏览器验真挂载。〔实测：纯 JSON → 装配 → 闸全绿 → 真挂载，标准部件零手写〕
- **深链**：装配骨架支持 `?sys=<系统key>&page=<页面id>` 直达指定系统+页面（截图自动化 / 回路闸用）；无效值回退首页。

> ⛔ **铁律·禁手搓交付原型 + 交付必过闸（2026-08-13 固化·强制）**
> 1. **任何要给用户看 / 交付的原型页面 HTML，一律不许用 Write 直接手搓产出**。原型页只能走 `qa/assemble-prototype.js`（模式1 标准骨架）或 `qa/inject-latest-anno-layer.js`（模式2 定制外壳）产出——管线外手搓的独立 `.html` **不算交付物**。
> 2. **任何原型文件在对用户说"完成 / 好了"之前，必须 `node qa/deliver-gate.js <原型.html>` 跑到全绿**；没喂进闸、或没过闸的，禁止宣称交付。
> 3. **为什么是红线**：手搓页静默逃逸全部机器闸（无 `__PRD_DATA__` / `__DESIGN_CHOICE__` / 标准件），且将来**导不了研发版**（拿不到料）——发票手搓版即前车之鉴。deliver-gate ㉝ 对「缺标记且无豁免」判红能兜底，但**只有把文件真的喂进闸才拦得住**：所以"每个交付原型都过一遍闸"是**人的纪律红线**，机器只兜"喂进来的那些"。
> 4. **例外**：纯示意的单页片段（如邮件模板、静态落地页）确需 Write 时，① 不得混进"原型/系统"交付物冒充可操作原型，② 仍须浏览器截图眼验，③ 明确告知用户"这是静态页、未过原型闸"。

### 🛠 出问题怎么【自查自修】（任何 AI 工具照此办 · 不靠特定 AI/人）

**别人装了包，画原型 / 标注功能出问题时——不用找原作者，让手边的 AI 照这套机器闸自己定位、自己修、自己验：**

1. **一键跑总闸看哪坏**：
   ```
   node skills/pm-design/qa/deliver-gate.js
   ```
   红的每一道**都会明确指出坏在哪**（例：「⑰缺契约恢复标注接桥」「㉔清空→标注没清零」「㉓导出分享版仍含没标注不让导拦截」）。总闸含 ~24 道：静态地雷/标注层回归/契约/端到端/**㉔标注功能真机(默认关·4按钮·圈选·面板·清空·恢复)**/⑯圈选↔注入回路/⑰原型↔标准件漂移/⑧⑪⑫PRD合规/㉓分享版只读+导出规则 等。
2. **照红字改·改【源头单一真理源】不改单个原型**：所有"正确长什么样"都在 `components/`（annotation-layer.html 标注层引擎 + host-shell.html 顶栏工具条 + page-renderer.html 渲染器 + prototype-skeleton.html 骨架）。红字指向哪个契约/功能，就去对应 components 文件修——**禁只改某个原型文件**（那是拆东墙补西墙、别处还会红）。
3. **改完把最新标准件同步进已有原型**：定制外壳原型用 `node qa/inject-latest-anno-layer.js <原型> <原型>`（就地重注入最新标注层）；标准骨架原型直接 `node qa/assemble-prototype.js` 重装。
4. **重跑总闸必须全绿**才算修好——`node qa/deliver-gate.js` + `node qa/three-principles-conformance.js` 都 0 退出码。绿了 = 三原则(本地/打包别人/任意窗口画新原型都达当前效果)成立。

> **核心**：这套是【机器闸驱动·自描述】的——"正确"编码进闸、"标准"锁在 components 单源。**任何 AI 跑闸→读红→改单源→重跑绿**即完成自修，不依赖原作者。**新功能/新规则每次都要补一道闸**（否则闸覆盖不到=又退回"靠人发现"）。

### 🏛 标注层组件铁律（v1.1 强制 · 独立实例解耦 / 杜绝重写返工）

生成任何新原型时，标注层（pin 标注系统 + 框选 + 内联编辑弹窗 + AI 命令栏）**必须从 [components/annotation-layer.html](./components/annotation-layer.html) 整段原样注入，禁止凭记忆重写**。

**Why**：标注层 JS 交互引擎（框选/查看编辑双态/内联编辑/持久化）每次重写都会重复犯同一批 bug（const 重复声明导致 Vue 挂不上、框选气泡漂移、区域识别错位）。组件是逐 bug 调试通的字节级稳定版。

**★ v1.1 解耦铁律（B方案 · 根治"标注层崩→Element Plus 业务页整页白屏"）**：
标注层挂【独立 Vue 实例】到 `#anno-app`，与业务 `#app` **物理隔离**——禁止再把标注层 ③ 引擎并入业务 `setup()`、禁止把 ④ 键并入业务 `return`。带 `app.config.errorHandler` 隔离，标注层内部抛错只崩自己，业务页照常。已 Playwright 实测（archive/EP解耦验证-2026-06-22.html + 标注层v1.1注入试跑-2026-06-22.html）。

**How — 注入必须包含六段（缺任一段 = 不完整）**：

| 段 | 位置 | 说明 |
|---|---|---|
| ① style | `<head><style>` | 标注层样式（全局，沿用） |
| ② HTML(#anno-app) | `<body>` 内，业务 **#app 结束标签之后**（不再塞进 #app） | 包在 `<div id="anno-app">` 内 |
| ③ setup() JS | 业务脚本**之后**（自带 `createApp().mount('#anno-app')`，**勿并入业务 setup**） | 核心引擎逻辑 |
| ④ return | 已内置于 ③ 独立实例，**业务 setup 无需合并** | — |
| **⑤ SSE 自动刷新** | **`</body>` 前（强制）** | PRD 更新后原型自动刷新，无需手动 F5 |
| ⑥ 宿主三件事 | 业务 setup / nav | 放 #anno-app；`window.__annoSetView(sys,page)` 桥接视图；nav 标注开关/生成PRD/扫描遗漏按钮改调 `window.__anno`（不再 v-model 标注 ref） |

**★ 旧原型（v1.0 焊进单 setup 的）升级注意**：那类原型标注层与业务焊在同一个 createApp（且常有 `:data-annotation="ak(...)"` 业务模板绑定依赖标注 setup 的 `ak`），**不能简单删插**——优先按 v1.1 重新生成原型，或谨慎评估后再做解耦改造（充值管理/存货核算即属此类）。

**打开已有原型铁律（强制自检，不需要询问用户）**：
AI 打开或修改任意原型 HTML 时，必须检查是否含 `initSSEAutoRefresh`：
- **不存在** → 立即将 annotation-layer.html ⑤ 段补注到该原型 `</body>` 前
- **存在** → 跳过

**框选卡片识别铁律（防"功能区"通用内容 bug）**：
框选代码中卡片标题选择器必须使用通配规律变量 `_CARD_TITLE_SEL`（含 `[class*="-card"] [class*="-label"]`、`[class*="stat-"][class*="label"]` 等），**禁止只枚举具体类名**。枚举类名会在新页面 CSS 命名下复现"功能区"bug，通配规律覆盖所有 SaaS 常见命名。

4. 组件是**产品形态无关的通用引擎**（适用 APP/小程序/网站/所有 B 端）；业务内容来自 `window.__PRD_DATA__`，组件内**禁止出现任何具体业务词**。
5. 内容生成层 `genAnnoDraft` / `_auditDraft` 按组件 ③-C 适配指引实现（内容随项目业务变，不字节固定；遵守 [annotation-templates.md](./annotation-templates.md) 第 24-28 条）。
4. 注入后**必跑自检**：grep 无 `const` 重复声明、无业务词残留；浏览器验收框选+查看/编辑态正常（见 [verify-prototype](../verify-prototype/SKILL.md) §6 防坑表）。

## 🏛 标注内容生成标准流程（强制 SOP · 先读标准再生成，禁止自作主张）

> 🔒 **架构铁律（2026-06-22 锁定）**：**PRD 内容（字段规范+用例规则）只由对话框 AI 真推理生成（通道①）→ `/anno-inject` 精确注入到目标 fp**；**原型点选/框选（通道②）只负责"圈范围"——标记是哪个功能点（data-annotation/入队），不在原型客户端生成内容**。客户端 `genAnnoDraft` 启发式仅作兜底草稿，不是主路径（它只能看 DOM 猜，结构性会错配）。理由+竞品印证见记忆 [[project_architecture_dialog_generates_prd]]。
>
> **适用**：任何时候生成 / 优化「字段规范 + 用例规则」标注内容（对话框① / 批量优化队列 / 直接重写 prd-data.json / window.__PRD_DATA__）。
> **本流程是强制做事顺序，AI 不得跳过 Step 1 凭记忆/凭理解直接编写。**（2026-06-22 固化：曾因未先读模板、自创格式导致字段规范/用例规则不合规返工。）
>
> **三料齐全铁律**：生成内容必须同时结合 **① 实际场景（该原型里这个功能真实怎么操作的）+ ② PRD skill 标准模板 + ③ 行业基线**，三者缺一不可——光套模板=脱离业务，光看场景=不合标准，光行业基线=没业务规则。

> 🔒 **B 流程交互铁律（2026-06-23 固化 · 用户逐条确认 · 禁止再违反）**：
> 1. **圈选=空待生成**：第一次点/框圈选（还没在对话框生成）时，标注弹窗的字段规范/用例规则**必须为空**（字段规范显示"暂无字段规范"，用例规则无任何节）；状态显示**"待生成"**。内容**只在对话框真推理生成+注入后**才出现，状态才变"已生成"。→ 圈选只建空 PIN，`genAnnoDraft` 不得往 PIN 塞内容；状态判定**只看 prd-data 是否有该 fp 的 field_specs/use_cases**，不看 PIN 客户端草稿。
> 2. **复制入口**：「📋 复制已圈功能」是**顶部唯一入口的按钮**（开「已圈定功能清单」面板）；**禁止塞进每个标注弹窗**。标注弹窗里可有「复制已圈功能」=只复制本功能（单条）。
> 3. **归属=上家菜单（通用，不写死层级）**：圈的任何元素（含框选的页签/数据看板等区域）都**归属于它所在的菜单**，必须能绑定到对应功能点，fpKey 命名与其他功能一致（如状态页签隶属充值管理→`充值管理-WMS.查询`）。归属路径由 **prd-data 的菜单结构派生**——B 端是 系统›一级›二级›三级菜单，APP/网站各自不同；**标准件只显示 prd-data 给的路径，绝不硬编码 B 端层级**（标注层是产品形态无关的通用引擎）。凡可圈选的容器（页签栏/筛选区/工具栏/分页/数据看板/表格/表单/弹窗）都必须贴 `data-annotation`，否则圈了会"未绑定"。
> 4. **清单完整跨系统**：「已圈定功能清单」不按当前视图过滤，**列出所有系统/视图**圈定的功能，带「系统/视图」（或归属路径）列。
> 5. **标注开关=el-switch**（做成开关非文字）；**标注模式底栏只留「清空」**+引导语（生成/反馈/导出/客户端自动圈 全去掉，生成统一走对话框）。
> 6. **生成新 PRD 绝不覆盖老的**：PRD.md/.docx 用新文件名（不撞老的）；注入前先备份目标原型；anno-server 回写只改 system_name 匹配的那个原型（见 [[project_anno_server_writeback_safety]]）。
> 7. **每次改完必跑回归闸 + 改了 UI/引擎必 bump 版本戳**；新坑先往闸加断言再修。

> 🔒 **PRD 生成两层分工铁律（2026-06-23 固化 · 各司其职）**：标注/圈选 → 生成 PRD 时，**结构与内容分两层，各归各家**：
> - **结构层（确定性）= anno-server 装配**：§4.4 系统 → 变长菜单树 → 功能点 → `.1 位置 / .2 原型图 / .3 字段规范 / .4 用例规则`、多系统、同名双写、编号顺延——**严格遵循 [`../prd/_rules/prd-directory-numbering.mdc`](../prd/_rules/prd-directory-numbering.mdc)**，不在此重造。
> - **内容层（真推理）= AI 按 prd skill 生成**：字段规范 5 列、用例规则 7 节、消息通知、操作日志——**严格遵循 prd skill 的 [`../prd/_rules/prd-template-structure.mdc`](../prd/_rules/prd-template-structure.mdc) + 模板 + quality-checklist**；pm-design **绝不重写** PRD 内容规则（各司其职，defer 到 prd skill）。
> - anno-server 只把 AI 产出的内容**原样插入**对应子节；客户端死模板 `genAnnoDraft` 已停用，**绝不用它猜内容**——这是之前点选/框选 PRD 质量差的根治。详见 [[feedback_task_follows_its_skill]] [[feedback_scan_existing_rules_first]]。

> 🔒 **功能名命名铁律（2026-06-23 固化 · 用户确认）**：圈选功能的「功能名」按模式取：
> - **点选**（按钮 / 操作 / 图标）→ **取该被点元素自己的可见文字**（导出 / 查看 / 编辑 / 删除）——按钮叫什么就显示什么。**技术铁律（2026-06-24 修 Bug）**：取 `target.closest('button,.el-button,[class*=btn]').textContent`（去括号计数 + 去空白），**绝不取祖先工具栏的 `data-annotation`/fpKey 功能段**——按钮自身没 data-annotation 时 `closest('[data-annotation]')` 会取到工具栏的 fp（如「导出」按钮取到「充值」fp → 名字错成"充值"）。fpKey 同步重定向到「祖先菜单段.按钮名」，让 AI 生成对的功能。框选 target=fakeTarget 无 closest 自动跳过此逻辑。

### 关键实现代码骨架

```js
// Excel 导出
const exportExcel = () => {
  const rows = [
    ['序号', '端/系统', '一级菜单/Tab', '二级菜单/页面', '功能点', '功能类型', '简述']
  ];
  let idx = 1;
  treeData.forEach(sys => {
    sys.children?.forEach(menu1 => {
      const hasLevel3 = menu1.children?.some(n => n.type === 'menu2');
      menu1.children?.forEach(menu2 => {
        const fps = hasLevel3 ? menu2.children : [menu2];
        fps?.forEach(fp => {
          rows.push([idx++, sys.label, menu1.label,
            hasLevel3 ? menu2.label : '',
            fp.label, fp.fpType || '', fp.desc || '']);
        });
      });
    });
  });
  const ws = XLSX.utils.aoa_to_sheet(rows);
  const wb = XLSX.utils.book_new();
  XLSX.utils.book_append_sheet(wb, ws, '功能清单');
  XLSX.writeFile(wb, `功能清单-${prdTitle}-${today}.xlsx`);
};
```

- ✅ **编号自动生成**：按业务对象类型（SPU/ORD/CST/DEV 等）自动生成下一个编号
- ✅ **弹窗 4 个关闭路径**：× / 取消 / 保存（校验通过+确认通过）/ ESC，关闭时 `resetFields()`
- ✅ **状态即时反馈**：状态变化立即反映到列表 Tag / 颜色 / 数值

1. **绝不臆造** —— 字段、布局、按钮、文案，只用规范已定义的；规范没有的进【待确认项】
