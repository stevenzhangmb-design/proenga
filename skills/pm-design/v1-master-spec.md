# pm-design v1.0 总规范（强制条款主索引）

> 🏛 **本文档是 pm-design skill 的 v1.0 主规范索引**——所有强制条款集中在此，详细内容引用各子文档。**AI 接到画原型任务前必须先读本文档**。

## 第一部分：工作原则

### 1. 以用户参考为准 + 发现问题主动提醒

**铁律**：用户提供的参考（截图 / 链接 / learned-specs / 之前发的样本）= **最高优先级真理源**。

**优先级层次**（高 → 低）：
1. 用户当前对话的参考（截图 / URL）
2. 用户之前学过的样本（[learned-specs/](./learned-specs/)）
3. PRD 铁律 + 标注层 + 原型业务流程规范（本文档第二~五部分）
4. 团队默认规范（[system-design-spec.md](./system-design-spec.md)）
5. AI 自己的想法（最低）

**发现冲突的标准句式**：
```
"我注意到 [参考里 XX] 与 [规范 YY] 不一致，可能处理：
 A. 完全按你的参考做
 B. 按规范改（理由：...）
 你倾向哪个？"
```

### 1.3 输出目录以使用者为准（铁律）

**所有生成文件（HTML 原型、PRD .md/.docx、流程说明、截图等）的存放路径，必须以当前使用者的实际环境为准，不得写死任何人的个人路径。**

- 首次接任务时，AI 主动问：「你的文件输出目录是哪里？」（给出默认建议：`./archive/`）
- 用户确认后，本次对话所有文件均存至该目录
- 规则文档 / skill 文件里出现的路径示例，一律用 `<输出目录>/` 占位，禁止写死绝对路径（如 `<某盘>:\<某目录>\archive\`）

---

### 1.4 用户需求的路径分流（v1.0 / 双主流程）

> 🏛 **核心铁律**：用户给输入时，AI 必须先判断走哪条主流程：**原型+PRD 联合** 还是 **PRD-only**。

| 用户场景 | 走哪条路径 | 使用的模板 | 上游 skill | 产出 |
|---|---|---|---|---|
| **要可点击原型 + PRD**（全新设计 / 竞品参考 / 新模块）| **原型+PRD 联合主流程** | [pm-design/prototype-prd-prompt-template.md](./prototype-prd-prompt-template.md) | pm-design + prd | 原型 HTML + prd-data.json + PRD .md |
| **只要 PRD 文档**（已有 UI / 外部协作 / 监管申报 / 评审场景）| **PRD-only 主流程** | [prd/references/templates/prompt-template-common.md](../prd/references/templates/prompt-template-common.md) | prd skill | 仅 PRD .md |

**判断关键词**：
- 用户说"画原型 / 帮我做一个 / 参考这个做 / 反推 / 学一下" → 联合主流程
- 用户说"写 PRD / 出文档 / 给监管的 / 外部评审用 / 已经有系统了只要 PRD" → PRD-only 主流程
- 用户没说清楚 → AI 必须主动问："你要原型 + PRD 三件套，还是只要 PRD 文档？"

### 1.5 竞品截图 / 链接的标准处理流程（Capture Mode / v1.0 强制）

> 🏛 **铁律**：用户给竞品截图 / 链接 + 说"按这个画"时，**必须先走 Capture Mode 反推画原型提示词流程**，不直接画原型。

**两步走**：
```
Step 1: AI 反推提示词 (.md) → 列出推测的字段/功能/框架/视觉 + 不确定点
Step 2: 用户核对 → 修改 → 说"按这个画" → AI 进入 Mode 1/2.2 真画
```

**Capture Mode 4 种工作方式**：
- 方式 1：竞品反推融合（截图/链接 + 增减）
- 方式 2：现有系统改造（截图 + 改动描述）
- 方式 3：AI 主动出方案（模糊需求）
- 方式 4：文档分析 + 系统建议（外部文档/RFP/大纲 → **两阶段：业务咨询 → 出原型**）— 详见 [business-analysis-template.md](./business-analysis-template.md)

**为什么不直接画**：
- AI 看竞品理解可能有偏差（截图局部 / 链接复杂）
- 直接画 → 用户发现错 → 返工成本高
- 反推 → 用户核对 → 偏差在出画前就发现

**标准模板**：4 种场景共用 [prototype-prd-prompt-template.md](./prototype-prd-prompt-template.md)（1 个核心 11 章节 + 场景化扩展节）。AI 按场景识别后填充方式不同。

**核心句式**（AI 收到竞品参考时必发）：
```
"我看到了 [竞品名/截图]，我会先反推一份「画原型提示词」让你核对，
 而不是直接画。这样能确保我理解的字段/功能/框架与你的预期一致。

 反推提示词包含：
 - 我推测的业务对象 + 字段（按 prd-data.json schema）
 - 我看到的功能点
 - 我推测的框架结构 + 视觉风格 + 交互细节
 - ⚠️ 不确定的点（请你确认）

 输出到 ./archive/画原型提示词-XXX-<日期>.md
 你核对后说"按这个画"，我再用确认版进入 Mode 1/2.2 真画。"
```

详见 [SKILL.md Capture Mode](./SKILL.md)。

详见 [SKILL.md 顶部"工作原则"章节](./SKILL.md) + memory `feedback_user_reference_priority`。

## 第一部分补充：多视图系统同名功能铁律

### 1.5 同名菜单 / 功能在不同系统视图下必须独立区分（铁律）

> **适用场景**：一个产品有多个系统视图（如 WMS 仓库端 + OMS 客户端、管理员视图 + 普通用户视图、B 端后台 + C 端前台），且两个视图中存在**菜单名称相同**或**功能名称相同**的情况。

**铁律：同名 ≠ 同内容。不同视图的同名功能，必须各自独立建 fp_key，用视图前缀区分，禁止共用 PRD 内容。**

| 规则 | 说明 |
|---|---|
| **1.5.1 fp_key 必须包含视图标识** | 格式：`<菜单名>-<视图标识>.<功能名>`，如 `账户余额-OMS.查询` vs `账户余额-WMS.查询` |
| **1.5.2 字段规范必须按视图真实 UI 写** | WMS 有客户筛选器 → field_specs 里写客户字段；OMS 无筛选 → 不写客户字段 |
| **1.5.3 用例规则必须按视图视角写** | WMS（仓库视角）："默认展示全部客户的账户余额"；OMS（客户视角）："固定展示当前登录客户自身的数据" |
| **1.5.4 前置条件写对系统名** | OMS 标注写"已登录 OMS"；WMS 标注写"已登录 WMS"；禁止两个视图共用同一条前置条件 |
| **1.5.5 genAnnoDraft 必须感知当前视图** | `sys.value`（WMS/OMS）必须传入 draft 生成逻辑，确保自动草稿内容匹配当前视图 |

**典型错误**：OMS 账户余额的「查询」标注，前置条件写"已登录 WMS"、操作流程写"展示全部客户余额" → 内容来自 WMS 视图，OMS 视图的 fp_key 缺失导致 fallback 到错误来源。

**正确做法**：
```
账户余额-WMS.查询 → 前置：已登录WMS + 可看全部客户 + 有客户/币种双筛选
账户余额-OMS.查询 → 前置：已登录OMS + 只看本客户 + 仅币种筛选（无客户筛选）
```

### 1.6 场景①（对话框）与场景②（原型内右键）彼此独立、可自由切换（铁律）

| 规则 | 说明 |
|---|---|
| **1.6.1 技术通道完全分离** | ①纯 AI 侧（读写文件）；②纯浏览器侧（读写 localStorage）；任一方故障不影响另一方 |
| **1.6.2 可随时切换** | ②右键不可用时，直接切到①对话框说"给 XX 生成PRD"；①AI 无响应时，直接切到②浏览器右键标注；两种方式产出的内容最终合并到同一份 prd-data.json |
| **1.6.3 数据时序规则（唯一合并点）** | ②在浏览器产生的 localStorage pins，**必须在使用①批量重新生成PRD之前**，先点「让AI更新PRD」同步到文件；否则 AI 不知道浏览器里的未保存标注，可能丢失 |
| **1.6.4 互不覆盖** | ①更新 prd-data.json + 回写 window.__PRD_DATA__，不清除②的 localStorage；②创建/编辑/删除 pins，不影响 AI 已生成的 .md/.docx 文件 |
| **1.6.5 混用是推荐用法** | 两种方式可以在同一个项目里混用，无需选边：复杂区域用①（批量、精准）；单个按钮/图标用②（可视化、即时） |

### 1.7 公共工具发布纪律：禁止泄漏个人 / 客户信息（铁律）

> 🏛 **本工具是面向外部用户的公共工具（会上传 GitHub / 打包分发）。任何进入版本库的文件，禁止包含个人本机信息或真实第三方客户信息。** AI 在生成、修改、整理任何要进仓库的文件时必须自检以下三类，发现即处理。

| 类别 | 禁止内容 | 正确做法 |
|---|---|---|
| **1.7.1 个人本机痕迹** | 个人绝对路径（`<某盘>:\<某目录>\archive\`、`C:\Users\<用户名>\...`、个人安装目录）、个人会话 ID、个人邮箱 / 用户名 | 一律用占位符（`<输出目录>/`、`<你的Chrome路径>`）；路径配置类文件（`.claude/settings.json`、`.mcp.json`）放进 `.gitignore`，另存同名 `.example` 模板供他人参考 |
| **1.7.2 真实第三方 / 客户系统标识** | 真实公司名、真实域名、真实业务文件名、真实备案号（如某客户 WMS 的域名 / 公司名） | learned-specs 等样本一律匿名化：公司→"某 XX 系统"、域名删除或改 `example-xxx.com`、文件 slug 用通用名（如 `wms-oms-sample`）；遵守 [learned-specs/README.md](./learned-specs/README.md) 法律边界——私有系统规范仅匿名后可分发 |
| **1.7.3 密钥 / 凭证** | API Key、token、密码、`ANTHROPIC_API_KEY` 实值 | 永不写入任何文件；用环境变量；`.env` 必进 `.gitignore` |
| **1.7.4 个人权限 / 确认配置** | 把个人命令放行规则（PowerShell/工具 allow 清单）、自定义快捷确认写进**会打包的** `.claude/settings.json` | 个人权限 / 放行**只写 `.claude/settings.local.json`**（本机个人配置，必进 `.gitignore`，**不打包**）；**绝不动 `settings.json`**（共享、会随 GitHub 打包，会改外部用户的确认习惯）。**铁律：别人用你的 agent，必须保留他们自己的默认确认习惯，不被你的本机配置改变。** 加放行前先确认 `settings.local.json` 已在 `.gitignore`（双保险） |

**触发时机（强制自检）**：
- 用户说"要上传 GitHub / 给别人用 / 做成公共工具 / 打包分发"时 → AI 主动全仓扫描上述三类（grep 个人路径、用户名、真实域名、密钥），列清单给用户确认处理方式（保留 / 匿名 / 删除）。
- 新建 / 改写任何要进仓库的规则文件、模板、示例时 → 示例里只用占位符和虚构数据，禁止顺手粘个人真实路径 / 真实客户数据。

**与 §1.3 的关系**：§1.3 管"输出文件路径以使用者为准"，§1.7 是其上位的发布纪律——不仅输出文件，**所有进版本库的内容**都要无个人 / 客户痕迹。

### 1.8 质量底线：0 错误交付 = 三道闭环（商业级铁律）

> 🏛 **诚实定义**：没有任何 AI 能保证"单次生成绝对零错"。本工具承诺的是 **「交付给研发的 PRD = 0 错误」**，靠**流程闭环**保证，不是赌 AI 单次完美。任何"AI 永不犯错"的承诺都是欺骗，禁止对用户这样说。

| 闭环 | 机制 | 拦截的错误 |
|---|---|---|
| **① 错配结构性杜绝** | 标注只认 `data-annotation` 精确绑定，**取消按名字模糊猜功能点**（见 annotation-templates 北极星「错配彻底根治」+ prd-data-schema §8 覆盖率自检） | 张冠李戴：跨视图 / 跨页 / 同名配错 → **真·0** |
| **② PM 确认门（不可跳过）** | AI 生成后 PM 核对，发现不对就改，**确认后才提交研发评审**（见标准工作流确认门） | 措辞 / 业务深度 / 字段错误 → 挡在交付前 |
| **③ 即时纠错** | 用户原型内【编辑】或对话框纠正，AI 按"用户为准"重生成；纠错可沉淀为规则/用例防复发 | 残余个例 → 当场修，同类不再犯 |

**AI 行为要求**：① 生成 PRD 时主动提示 PM"请核对后再提交研发"；② 用户问"能否 0 错误"时，按上面诚实定义回答（0 错误交付靠闭环，非单次完美），不过度承诺；③ 每修复一个错误，识别能否沉淀为规则/测试用例防复发（受 [[fix-must-solidify]] 门控）。

**纠错沉淀（防复发）**：用户每纠正一个 PRD 错误，AI 必须判断它是否属于"会复发的一类"；若是，按 [[fix-must-solidify]] 门控**提议**把它追加进 `regression-test-cases.md`（回归用例）+ 对应规则，使同类错不再出现。错误"越用越少"，而不是反复犯同一类。

### 1.9.0 框选卡片识别铁律（防"功能区"通用内容 bug）

> 历史 bug：框选选择器只枚举具体类名（如 `.stat-label`），新页面 CSS 命名变了就输出"功能区"通用模板。根治方法：通配规律。

| 条款 | 规则 |
|---|---|
| **1.9.0.1 禁止枚举具体类名** | 框选卡片标题选择器禁止写死 `.stat-label / .dcard-title` 等具体类名作为全集 |
| **1.9.0.2 必须用通配变量** | 必须定义 `_CARD_TITLE_SEL` 变量，包含 `[class*="-card"] [class*="-label"]`、`[class*="-card"] [class*="-title"]`、`[class*="stat-"][class*="label"]` 等规律选择器，覆盖 SaaS 常见命名 |
| **1.9.0.3 排除 Element Plus 表单组件** | 必须 `:not(.el-form-item__label):not(.el-checkbox__label):not(.el-radio__label)` 避免误抓表单 label |
| **1.9.0.4 卡片容器也用通配** | `closest()` 的卡片容器选择器同样加 `[class*="-card"]`，不能只列精确类名 |

#### 1.9.0bis 渲染器↔标注组件 契约铁律（防"现搓渲染器漂移"，2026-06-30 根因）

> **历史根因**：标注组件(annotation-layer.html)是"整段原样注入"的标准件，**但渲染器是每个原型现搓的**。某次原型把 stat-card 标签写成 `class="lab"`，而组件的 `_CARD_TITLE_SEL` 认的是 `stat-label / [*-label] / [*title]` → 框选卡片取不到名字 → 退回通用"功能区"。**现搓 = 必然漂移**，且没有任何闸逮得住，直到标注命名悄悄坏掉。
>
> **两条最高铁律（本节存在的理由）**：① 我画**新原型**时，必须达到本地已修好的效果；② **打包后**别人在其他 AI 工具里用，也必须达到同样效果。要 100% 做到，靠的是"共享件 + 机器闸"，不是自觉。

| 条款 | 规则 |
|---|---|
| **1.9.0.5 渲染器命名必须被组件认出** | 渲染器输出的卡片标签/标题类名，必须能被标注组件 `_CARD_TITLE_SEL` 识别——即**含 `label` 或 `title`**（标准件统一用 `stat-label / stat-value / stat-hint`，见 `qa/fixtures/reference-prototype.html`）。**禁止** `lab / val / note` 等组件不认的私造短类名。 |
| **1.9.0.6 区块必埋 data-annotation 锚点** | 渲染器每类区块（统计区 / 列表 / 自定义页）必须用 `ak(page, op)` 盖 `data-annotation` 锚点；自定义页(v-html)同样要埋，否则开标注后点选标不上、看不到 PIN。 |
| **1.9.0.7 机器闸必跑·红则禁交付** | 每次改完原型/渲染器，**必跑** `qa/renderer-contract-gate.js`（零依赖静态闸，判断标准从组件源码实时抽 `_CARD_TITLE_SEL`、与组件永不脱节）。① 画新原型时跑 → 兜住铁律①；② 随版本库打包、别人也能跑 → 兜住铁律②。红=渲染器漂移，禁交付。 |
| **1.9.0.8 根治方向：渲染器收敛为共享件** | 终态：把渲染器（卡片/筛选/表格模板 + 类名 + 锚点）抽成 `components/page-renderer.html`，像标注组件一样**整段原样注入**——逐字节相同就**没得漂移**。项目各自不同的只有数据(NAV/PAGECFG)，效果由共享件保证一致。 |

### 1.9 客户安装铁律（商业分发强制）

> 本工具面向付费客户分发。**客户安装负担 = 最小化**，AI 不得在首次使用流程里要求客户装任何维护者侧工具。

| 条款 | 规则 |
|---|---|
| **1.9.1 客户必装（仅两样）** | ① **Node.js 18+**（运行 anno-server）② **pandoc**（生成 Word .docx；不要 Word 可跳过）。这两样以外，客户不需要额外安装任何东西。 |
| **1.9.2 客户已有（禁止重复要求安装）** | AI 工具（OpenClaw / Cursor / Claude Code / Codex 等）、浏览器——客户装插件前提已有，禁止在安装清单里列出。 |
| **1.9.3 维护者工具禁进客户流程** | 回归脚本（regression-check.ps1 / check-annotation-coverage.ps1）、Playwright 等 QA 工具是**维护者发版自检用**，不打包进客户包、客户不运行、不在客户文档里提及。 |
| **1.9.4 首次检测工具无关** | CLAUDE.md 的首次使用检测脚本只检 `node --version` + `pandoc --version` + anno-server 状态，**禁止检测任何特定 AI 工具**（如 `claude --version`）——客户用什么 AI 工具都能正常走流程。 |
| **1.9.5 路径无硬编码** | 所有进版本库的文件（CLAUDE.md / 规则文件 / 模板）禁止出现个人绝对路径（见 §1.7.1）；anno-server 路径用相对路径或占位符，AI 根据实际项目位置自动推断。 |
| **1.9.6 AI 引导安装** | 客户不需手动敲命令——检测到缺失时，提示"告诉 AI「帮我装 Node.js / pandoc / 启动 anno-server」，AI 全程引导"。 |

## 第七部分：通用禁止 / 正确做法清单

### 禁止做法（任何场景都禁，违反 = 必须删除后重写）

- ❌ 点保存只弹"成功"toast，列表里看不到新数据
- ❌ 点删除只弹 Toast，列表里数据没消失
- ❌ 点启用/停用只弹 Toast，状态 Tag 没变
- ❌ 表单字段没 `:rules`，随便填都能提交
- ❌ 校验错误用 alert / 顶部 Toast（应该用 el-form-item 默认在字段下方红字）
- ❌ 业务前置校验缺失（如删除时不检查关联依赖）
- ❌ 编号不自动生成（让用户手填）
- ❌ 弹窗关闭路径被屏蔽（× / 取消 / ESC）
- ❌ 菜单点击每次都弹 toast"已切换到 XX"
- ❌ ⓘ 标注挂在 H2 模块标题 / 面包屑 / 菜单旁
- ❌ H2 模块标题与面包屑信息重复
- ❌ 仅 `app.use(ElementPlus)` 不解构 ElMessage/ElMessageBox
- ❌ 看到用户参考的"问题"默默"修正"成自己认为对的样子
- ❌ 凭空臆造参考里不存在的字段 / 控件

### 正确做法（任何场景都必须）

- ✅ 用户填错字段 → 离开字段 → 字段**下方**立即出现红字
- ✅ 用户点保存 → 多个字段**同时在各自下方**显示错误
- ✅ 提交成功 → 列表**立即**出现新行 / 更新行 / 少一行 / 状态切换
- ✅ 业务前置校验**先于二次确认**执行
- ✅ 编号自动按业务对象类型生成
- ✅ 关闭弹窗后自动 `formRef.resetFields()`
- ✅ 状态变化即时反映到列表
- ✅ 菜单切换静默 + active 高亮
- ✅ B 端必有页签导航
- ✅ ⓘ 挂在功能点入口按钮
- ✅ 优先按用户参考做，发现冲突主动 ABCD 选项提醒

**用户提供团队模版后 AI 必做的事**：
1. 把团队模版存到对应 skill 目录下（如 `tech-design/team-template.md`）
2. 更新 SKILL.md 切换"模板来源"为团队模版
3. 重新生成已有的文档（按团队模版覆盖）

**AI 在生成下游文档时必须告知用户**：
```
"已按【行业通用规范】生成 <文档类型>。
 如有团队特有的文档模版，请提供，我会立即按团队模版覆盖生成。"
```

#### 9.4 各文档共享的元数据头

这保证 4 类文档之间的可追溯性 + 单一真理源。

### 10.2 Phase 1 — 原型 + PRD 的 4 种触发场景

| 场景 | 触发条件 | AI 行为 | 输出 |
|---|---|---|---|
| **场景 1**：竞品参考 + **无提示词** | 用户给竞品截图/链接 + 说"按这个画" | **AI 反推画原型+写PRD的提示词**（不直接画）→ 用户核对 → 用户说"按这个画" → 画原型 → 出 PRD | 反推提示词 .md → 原型 → PRD |
| **场景 2**：竞品参考 + **有提示词** | 用户给截图/链接 + **已写好提示词** | AI **直接按用户提示词画原型** → 出 PRD | 原型 → PRD |
| **场景 3**：**现有系统增量改造** | 用户给现有系统截图 + 提示词"加 X 功能/字段" | AI 在现有页面上**补全缺失功能 + 重新布局排版** → 出增量 PRD | 重画的原型（含旧+新）→ 增量 PRD |
| **场景 4**：**全新模块** | 无截图，仅文字描述 + 菜单结构 | AI 按规范画原型 → 出 PRD | 原型 → PRD |

### 10.3 Phase 1 内部循环：PRD ↔ 原型标注双向同步（v1.0 关键新增）

> 🏛 **铁律**：**prd-data.json 是单一真理源**。原型与 PRD 的字段规范/用例规则任意一方变化，都通过 prd-data.json 同步到对方。

```
[原型改了]                              [PRD 改了]
     ↓                                     ↓
[更新 prd-data.json]                [更新 prd-data.json]
     ↓                                     ↓
[原型标注层自动显示新数据]          [原型标注层自动显示新数据]
     ↓                                     ↓
[PRD .md 重新生成]                  [原型 HTML 重新生成]
```

**双向同步触发**：
- 用户说"原型 X 字段改成 Y"→ 更新 prd-data.json → 原型 + PRD 都同步
- 用户说"PRD §3.X 字段约束改成 Y"→ 更新 prd-data.json → 原型标注 + 原型可能样式都同步

**同步实施细节**：
1. **任一变更**：找到 prd-data.json 对应字段/用例规则节点更新
2. **原型 HTML**：重新生成，标注层从 prd-data.json 拉取显示新数据
3. **PRD .md**：重新生成，章节内容从 prd-data.json 重渲染
4. **变更日志**：所有文件头都加变更点说明

### 10.3.5 Phase 1 → Phase 2 衔接：PRD 范围控制（v1.0 强制）

> 🏛 **铁律**：原型 OK 后，AI **不能默认全写 PRD**，必须主动问范围。

| 用户说 | AI 做 |
|---|---|
| "出整个原型的 PRD" / 不指定 | PRD §4 包含全部菜单功能 |
| "对【X】写 PRD" | PRD §4 只包含 X 章节 |
| "对【X + Y】写 PRD" | 包含 X+Y |
| "对【X - 查询/新增】写" | 细粒度到功能点 |
| "对【除 Z 外】所有功能写" | 排除 Z |
| "本期 A/B，下期 C/D" | 当前 PRD 只含 A/B，C/D 标注"下期再写" |

AI 标准句式（Step 5 必发）：
```
"原型 OK！请告诉我对哪些菜单/功能点写 PRD：默认全部，可指定（菜单/组合/功能点/排除/版本）。"
```

### 10.4 Phase 2 — 设计文档并行生成（原型+PRD 确认后）

**并行生成**：用户可一次说"同时生成技术设计和测试用例"，AI 并行输出 2 个文档。

### 10.5 Phase 3 — 研发提示词（技术设计确认后）

| 文档 | Skill | 依赖 | 触发 |
|---|---|---|---|
| 研发提示词集 | [dev-prompts](../dev-prompts/SKILL.md) | **原型 + PRD + 技术概要设计** | 用户说"生成研发提示词" |

**依赖顺序强制**：研发提示词必须在技术设计**之后**生成，因为提示词要引用技术设计的：

- 状态机

### 10.6 所有 5 类下游文档：AI 主动提醒 + 用户决定（v1.0 通用铁律）

> 🏛 **核心铁律**：5 类下游文档（PRD / 技术设计 / 测试用例 / 研发提示词 / 操作手册）AI 都必须在**前置依赖完成后主动提醒**用户，让用户决定何时生成。**不能沉默不催，也不能自动触发**。

#### 10.6.1 6 类文档提醒时机表

| 文档 | Skill | 前置依赖 | 触发提醒时机 |
|---|---|---|---|
| **PRD** | prd | 原型核对确认 | 用户说"原型 OK"时 |
| **技术概要设计** | tech-design | PRD 核对确认 | 用户说"PRD OK"时 |
| **测试用例** | test-case | PRD 核对确认 | 用户说"PRD OK"时 |
| **研发提示词集** | dev-prompts | 技术设计核对确认 | 用户说"技术设计 OK"时 |
| **操作手册** | user-manual | 原型 + PRD 确认 | Phase 1 确认时 + Phase 2/3 完成时各 1 次 |
| **售前产品方案** 🆕 | product-pitch | **user-manual 先生成或同时** | user-manual 生成后立即提醒；或用户说"同时生成"时一起做 |

#### 10.6.2 AI 主动提醒的标准句式

```
"📄 <文档名>（<skill>）现在可以生成了。
 <一句话作用说明>
 你想：
   A. 现在就生成
   B. 稍后再生成（<暂缓时机说明>）
 默认我会等你说"生成 X"再做。"
```

#### 10.6.3 5 类文档的标准提醒模板

**PRD 提醒**（原型确认时）：
```
📄 PRD（prd）可以生成了。这是完整产品需求文档（含字段规范/用例规则/业务流程）。
你想：A. 现在就生成 / B. 稍后（原型可能还要微调）。
默认等你说"生成 PRD"。
```

**技术概要设计 + 测试用例并行提醒**（PRD 确认时）：
```
📐 技术概要设计（tech-design）+ 🧪 测试用例（test-case）现在可以并行生成了。
- 技术设计：架构 / 数据模型 / API / 状态机（给研发）
- 测试用例：55+ 用例（给 QA）
你想：A. 同时生成两个 / B. 只生成一个 / C. 都稍后。
默认等你说"生成 X"。
```

**研发提示词提醒**（技术设计确认时）：
```
🛠 研发提示词集（dev-prompts）现在可以生成了。
研发拿去喂给 Cursor/Copilot 直接出代码（前端+后端+DB+测试+DevOps 30+ 提示词）。
你想：A. 现在就生成 / B. 稍后（等研发组进场再生成）。
默认等你说"生成研发提示词"。
```

**操作手册提醒**（Phase 1 确认时 + Phase 2/3 完成时各 1 次）：
```
📖 操作手册（user-manual）现在可以生成了。给最终用户的文档（功能介绍/操作步骤/FAQ/故障排查）。
你想：A. 现在就生成（早生成可同步内部 review）/ B. 上线前生成 / C. 上线后生成。
默认等你说"生成操作手册"。
```

#### 10.6.4 提醒频率铁律

- ✅ **前置依赖确认时必提醒 1 次**（每个文档独立计数）
- ✅ 用户说"暂缓" → 后续关键节点（Phase 切换时）**再提醒 1 次**（不要遗忘）
- ✅ 用户说"不再提醒 X" → 立即停止对 X 的提醒
- ❌ 禁止：用户没问就完全沉默（用户会忘）
- ❌ 禁止：每次对话都催（变骚扰）
- ❌ 禁止：自动触发生成（必须用户说"生成 X"才做）

#### 10.6.5 用户响应处理

| 用户响应 | AI 行为 |
|---|---|
| "生成 X" / "现在就生成" / "可以" | 立即触发对应 skill |
| "稍后" / "暂缓" / "等等" | 记住，下个关键节点再提醒 |
| "不要再提醒了" / "不提醒了" | 立即停止该文档的提醒 |
| 用户继续别的话题 | 不强求，转去做别的，关键节点再提醒 |

### 10.7 阶段间的"确认门"（Quality Gate）

| 门 | 必须确认的内容 | 不通过的后果 |
|---|---|---|
| **Gate 1**：原型 → PRD | 原型 UI / 字段 / 功能点 / 框架结构 | 重新画原型 |
| **Gate 2**：PRD → Phase 2 | PRD 字段规范 / 用例规则 / 业务流程 | 修改 PRD（双向同步原型）|
| **Gate 3**：技术设计 → 研发提示词 | 数据模型 / 接口契约 / 关键决策 | 修改技术设计 |

**AI 必须在每个门主动询问**："X 已生成，请你核对，确认后我进入下一阶段。"

### 10.8 工作流的核心铁律

1. ✅ **顺序强制**：Phase 1 → Phase 2 → Phase 3；Phase 4 独立但需 Phase 1 完成
2. ✅ **确认强制**：每个阶段必须用户确认 ✅ 才能进入下一阶段
3. ✅ **双向同步**：Phase 1 内部，原型与 PRD 任意一方变化都更新 prd-data.json，对方同步
4. ✅ **单一真理源**：prd-data.json 是所有下游文档的源头
5. ✅ **主动提醒 + 用户决定**：**5 类下游文档**（PRD/技术设计/测试用例/研发提示词/操作手册）AI 都必须在前置依赖确认时主动提醒（含选项），但生成时机由用户决定；用户说"不再提醒 X"则停
6. ✅ **并行生成**：技术设计 + 测试用例可并行（Phase 2 内部）
7. ❌ **禁止跳阶段**：禁止用户说"原型还没确认就出技术设计" / "技术设计没确认就出研发提示词"
8. ❌ **禁止单向同步**：禁止只更新原型不更新 PRD（或反之）
