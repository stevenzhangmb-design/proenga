# Product-Pitch Skill — 售前产品方案

## 触发场景

| 触发 | 示例 |
|---|---|
| 原型 + PRD 确认后 | "出一份售前方案 / 产品方案介绍" |
| 显式指令 | "生成售前 PPT / 客户讲解材料 / 投标技术方案" |
| 新模块对外传播 | "把这个新功能写成销售材料" |

## ⚠️ 生成顺序铁律（必须）

**本 skill 必须在 [user-manual](../user-manual/SKILL.md) **之后或同时**生成，不能独立于 user-manual 之前**（也登记在 [../_shared/downstream-skill-conventions.md](../_shared/downstream-skill-conventions.md) 跨技能生成顺序）。

```
✅ 正确顺序：操作手册 → 售前方案
✅ 也正确：操作手册 + 售前方案 同时生成
❌ 禁止：售前方案独立先生成（业务理解不扎实）
```

**AI 行为**：
- 用户说"生成售前方案" → AI 先检查 user-manual 是否已生成
  - ✅ 已生成 → 立即开干
  - ❌ 未生成 → 提醒："建议先生成操作手册，业务理解更扎实。是否一起生成？(A 一起生成 / B 先操作手册再售前 / C 跳过操作手册直接售前)"

**理由**：
- 操作手册的"业务术语 + 场景"会成为售前方案"业务对象命名"的来源
- 售前方案的"功能亮点"需要操作手册级别的细节支持

## 输入

1. **prd-data.json**（菜单 + 功能点）
2. **原型 HTML**（截图素材）
3. **PRD .md**（业务理解）
4. **可选**：[learned-specs/saas-product-pitch-style.md](../pm-design/learned-specs/saas-product-pitch-style.md)（标杆样本）+ 公司信息（成立时间 / 融资 / 荣誉 / 客户数等）

## 输出

PPT 大纲式 Markdown（可转 PPT），前缀 `产品方案`，输出目录 / 命名 / `.docx` 同步均按公共约定 [../_shared/downstream-skill-conventions.md §1](../_shared/downstream-skill-conventions.md)。

## 文档结构（4 大部分 / 标杆水准）

**学习自行业标杆 WMS 34 页 + 另一标杆 WMS 19 页提炼的标准 4 部分**：

```
01 关于公司 / 产品          → 建立可信度
02 行业痛点 & 业务场景       → 引发共鸣
03 全面领先的解决方案 + 功能亮点 → 展示产品力（主体）
04 为什么选择我们            → 决策助推 + CTA
```

详细模板见 [template.md](./template.md)。

## 强制生成清单（行业标杆 WMS 9 要素 / 缺一不可）

> 🔒 **铁律**：以下 9 个要素必须全部出现在输出中，缺少任何一个 = 不达标，必须补齐后再交付。

| # | 要素 | 对应模板页 | 禁止省略的理由 |
|---|---|---|---|
| 1 | **目录页**（4 大模块编号 + 名称）| P2 | 建立结构感，让客户知道要看什么 |
| 2 | **痛点单页深挖**（4 大场景，每场景 4-5 个痛点）| P11 | 共鸣是购买决策的第一驱动力 |
| 3 | **业务流程图**（含 WMS/OMS 端 + 角色框 + 闭环）| P12-P15 | 专业感来源，区别于 PPT 堆砌 |
| 4 | **系统功能矩阵图**（全模块展开）| P19 | 让客户看到"全面性"，消除功能盲点顾虑 |
| 5 | **业务场景全景图**（中心辐射 5-6 大模式）| P20 | 场景化命名比功能模块更能打动业务决策者 |
| 6 | **每模块功能亮点页**（每模块 1 页，3-8 个亮点）| P21-P29 | 产品力证明的核心载体 |
| 7 | **量化效果数据**（5 个 KPI 数据，如 99%/53%）| P18 | 数字说服力 >> 文字描述 |
| 8 | **三大优势分类**（产品优势 + 服务优势 + 资源优势）| P31-P33 | 推动最终决策的差异化证明 |
| 9 | **发展历程时间轴 + 用户增长曲线** | P6 | 建立可信度（有历史 = 有沉淀）|

## 视觉风格约束（铁律）

> 适用于所有 B 端 SaaS 产品方案，不可随意改动。

| 维度 | 约束 |
|---|---|
| **主色** | 蓝色（B 端 SaaS 标配）+ 大面积留白 |
| **数字呈现** | 大数字 + 单位 + 一行说明：`320W+ 服务全球用户` / `99% 准确率` |
| **功能描述** | 加粗能力名（4-6 字）+ 一句话价值（15-25 字）：`**智能波次打单**：缩短拣货路径，提升出库效率` |
| **章节封面** | 全屏品牌色 + 大号编号（01/02/03/04 描边字）+ 大字号模块名；仅 1 行内容 |
| **业务场景命名** | ✅ 用业务对象名：`一件代发` / `备货中转` / `退货换标`<br>❌ 禁用模块名：`出库管理` / `入库管理` / `退货管理` |
| **图形语言** | 图标矩阵 + 流程图 + 中心辐射图；禁止纯文字 bulleted list 代替图形 |

## 核心设计原则（来自标杆案例）

| # | 原则 | 应用 |
|---|---|---|
| 1 | **业务对象命名**（不是模块名）| "一件代发"而非"出库管理"<br>"会员等级"而非"会员模块" |
| 2 | **数据公式**：大数字 + 单位 + 一行说明 | `320W+ 服务用户` / `99% 准确率` |
| 3 | **功能描述公式**：加粗能力名 + 一句话价值 | "**智能波次打单**：缩短拣货路径，提升出库效率" |
| 4 | **每模块 3-8 个核心亮点**（不超载）| 核心业务 6-8 个，管理类 3-4 个 |
| 5 | **业务流程图必出**（B 端 SaaS）| WMS 端 + OMS 端 + 角色框 + 闭环 |
| 6 | **章节封面必出**（4 大部分）| 全屏背景 + 编号 + 模块名 |
| 7 | **量化效果必出**（说服力）| 99% / 53% / 70% / 39% 类数据 |
| 8 | **三大优势分类**（产品 / 服务 / 资源）| 决策助推标配 |

## 与 prd-data.json 的映射规则

> 字段语义以 schema 真理源 [../pm-design/prd-data-schema.md](../pm-design/prd-data-schema.md) 为准；下表只做 schema 字段 → 售前方案章节的映射，不重定义字段语义。

| prd-data.json 内容 | 对应章节 |
|---|---|
| menus 一级菜单 | §3 解决方案 - 业务场景全景图（中心辐射）|
| menus 二/三级菜单 | §3 解决方案 - 各业务模块功能亮点页（每页 1 个）|
