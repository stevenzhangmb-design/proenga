# PRD

> 🏛 **提速铁律（随包·三条产线通用）**：生成原型 / 写 PRD / 生成代码，**不管从 0 生成还是中途改**，一律按 [`skills/_shared/speed-protocol.md`](../_shared/speed-protocol.md) 走快路；同一个动作失败 2 次就停下说话，禁死循环。

> 🏛 **本 skill 100% 遵守 [_rules/](./_rules/) 下的铁律——任何冲突以 [_rules/prd-template-structure.mdc](./_rules/prd-template-structure.mdc) 为准；本 SKILL.md 不复述、不覆盖铁律。**

## ⚠️ 四条顶级红色铁律（PRD 必过）

- **R-A 图片识别 5 段绝不进 PRD 文件**：`图片绑定表 / 图片识别结果 / 图片归档清单 / 待确认项 / 合理化建议` 仅作对话辅助输出，**严禁**写入 PRD `.md` 文件；PRD 引用图片只用 `IMG-xx` 编号。
- **R-B PRD 固定 4 章**：仅 1 开发目的 / 2 版本变更 / 3 术语 / 4 功能需求；功能点直挂第 4 章对应末级菜单下（`##### 4.4.x.y` → `###### 4.4.x.y.z`），严禁另起 `## 5`。
- **R-C 字段规范仅收录数据字段**：按钮 / 操作链接 / 底部操作区 / 关闭图标等非数据元素一律不进字段表，由 `用例规则-操作流程` 承载。
- **R-D PRD 须用户触发，AI 不得自行凭空撰写**：有原型→用户**点选/框选**圈定范围 + 对话框说"为 XX 生成 PRD"，AI 才真推理生成（anno-inject）；无原型→用户明确场景 A/B 并给输入后才生成。未经圈选/对话框触发即产出的 PRD 性质内容一律违规删除。竞品分析/方案等非 PRD 文档不受限，但不得以"方案"之名输出"字段规范+七项用例规则"行 PRD 之实。

详细判定标准与禁止形式见 [prd-template-structure.mdc](./_rules/prd-template-structure.mdc) 文件开头「顶级红色铁律」段。

> 🔴🔴🔴🔴 **没做完不许给肯定答复铁律（2026-11-09 用户明令「这个是铁律」）**：用户问 PRD 某处“改了吗/删了吗”，没改完第一句就答“没有/还没做完”；PRD 改动以 .md 和 .docx 都已更新、写法检查通过为“做好了”，只生成了别的文件或草稿不算。细则见 `skills/pm-design/SKILL.md §没做完不许给肯定答复铁律`。

> 🔴🔴🔴🔴 **不做无关的事铁律（2026-11-09 用户明令「这个是铁律」· 最高优先 · 随包）**：只动用户指定的那份 PRD（及其 Word）和对应原型；其他文档、其他原型不查、不改、不重新生成；公用件（模板、规范、`qa` 闸、骨架）不是用户要求的先问再改；派子任务要在指令里写死范围并要求列出动过的文件；钩子因无关文件拦截时不去处理它，如实告诉用户。细则见 `skills/pm-design/SKILL.md §不做无关的事铁律`。

> 🔴🔴🔴🔴 **先研究后建议铁律（2026-11-13 用户明令「工作底线」· 最高优先 · 随包）**：PRD 里的业务规则、状态设计、文案取舍要用户拍板时，给建议前必须先研究竞品和行业标准系统、本系统现状、行业规范和法规原文，建议里写明依据和证据等级；研究不够就说“还不能建议，缺……”。细则见 `skills/pm-design/SKILL.md §先研究后建议铁律`。

## 适用场景（PRD-only 主流程 / 无原型）

- "只要 PRD 文档，不需要原型"
- "把这个需求整理成 PRD 文档"
- "补齐验收标准/范围边界"
- "已有 UI 截图，只要 PRD"（外部协作 / 监管申报 / 评审）
- "在现有 X 模块加 Y 功能写 PRD"（**场景 A 文字增量**）
- "拖现有系统截图写 PRD"（**场景 B 截图驱动**）

⚠️ **如果你要 AI 画原型 + PRD 三件套** → 请走 [pm-design Capture Mode 联合主流程](../pm-design/prototype-prd-prompt-template.md)

## ⚠️ 2 种 PRD-only 场景（v1.0 / 都不画原型）

### 场景 A：文字增量改造（无原型，无截图）

- **输入**：现有模块菜单路径 + 改动文字描述 + （可选）旧 PRD 文件路径
- **AI 处理**：文字复述对改动的理解 → 用户确认 → 仅描述增量功能点，旧功能点用 `详见旧 PRD §x.y.z` 引用
- **输出**：**增量 PRD**（仅 §4 修改/新增部分，章节顺序保持，标"v1.X 增量"）+ 增量 `prd-data.json`
- **图片识别 5 段**：**跳过**（无截图）

### 场景 B：截图驱动（有现有系统截图，不画原型）

- **输入**：用户拖现有系统截图清单（直接填基础信息 + 业务背景）
- **AI 处理**：走 [references/standards/image-recognition.md](./references/standards/image-recognition.md) **5 段对话辅助流程** → 用户确认 → 生成完整 PRD
- **输出**：完整 PRD 4 章 + `prd-data.json`
- **5 段对话辅助**：图片绑定表 / 图片识别结果 / 图片归档清单 / 待确认项 / 合理化建议（仅对话输出，**严禁**写入 PRD 文件，铁律 R-A）

## 执行流程

1. 识别 Mode（见上）
2. 明确业务背景、目标用户、核心问题（**场景 A 时仅问最少必要**）
3. 收集约束条件（资源、合规）
4. 用 [references/templates/prd-template-clean.md](./references/templates/prd-template-clean.md) 作模板生成 PRD 初稿
5. 按 [_rules/prd-template-structure.mdc](./_rules/prd-template-structure.mdc) 校对字段规范、用例规则七项与操作日志等铁律
6. 用 [references/quality-checklist.md](./references/quality-checklist.md) 做成文自检
7. **⚠️ 生成后强制深检门（铁律，缺一不可）**：按 [_rules/prd-post-generation-deepcheck.mdc](./_rules/prd-post-generation-deepcheck.mdc) 执行四步——⑴ 全量通读规则原文（不靠记忆/摘要）⑵ 逐功能点对照每条规则全量深检细到标点（严禁抽检）⑶ 运行 `node qa/prd-structure-lint.js <PRD.md>` 退出码必 0 ⑷ 判断类逐条人工核、不擅自主张（有疑义问用户）。**未全绿不得告知用户"已完成"。**
8. 通过后输出
9. **⚠️ 双向同步（强制）**：每次更新 PRD 内容后，必须按 `CLAUDE.md §PRD双向同步铁律` 同步执行：
   - 更新 `prd-data.json` 对应功能点条目
   - 回写原型 HTML 的 `window.__PRD_DATA__`
   - 输出三步确认提示给用户

## ⚡ 生成提速（PRD 生成太慢的根治·2026-09-10·只做不伤质量的）

> **背景**：慢的是「AI 在对话框逐条写字段规范+7节用例规则」这段（anno-server 落文件很快）。以下三条只压缩「AI 要写的量/墙钟」，**不碰业务内容质量**。触发点 = 用户圈选功能 → 点【复制已圈功能】→ 粘进对话框（提示词已内嵌下述规则）。

1. **复用固定件·只写业务槽位（每个功能省 ~20-30%·格式永远对）**：7 节里的固定件——操作日志固定说明语+6行表头（[annotation-templates.md](../pm-design/annotation-templates.md) §9）· 查询/查看类固定写「查询/查看不输出操作日志。」（§27）· 提示消息表头 · 消息通知固定 4 列表头（§38）——**直接沿用已定义的，禁逐字重新推导重写**；AI 只写业务槽位（具体权限/校验/文案/接收方）。固定件本是标准件，复用=质量不降反稳。
   - 🔧 **工具（2026-10-08·把"复用固定件"从嘱咐变工具）**：`node skills/prd/prd-draft.js <类型> [--fields "售价*,库存"] [--notif] [--name 商品]` → 机器吐出该功能点的 **7 节 use_cases 骨架**：固定件（operation_log 固定说明语 / 查询类固定句 / prompt_messages「请输入X」/ 通知 4 列表头）**逐字填好**，业务处留 `<…>` 槽位；AI 只填 `<…>` 再 `/anno-inject`。类型：add/edit/delete/submit/audit/export/batch/query/view/filter/reset（查询类自动出"不输出操作日志"；提交/审核类自动出通知表）。固定件与真理源的一致性由 `qa/prd-draft-sync-gate.js` 守（漂移判红）。**它只省固定件重敲、保证格式，业务内容仍 AI 真推理写。**
2. **多功能并行（Claude Code·最大墙钟收益）**：一次圈了 N 个功能点，**扇 N 个并行子 agent 各写一个功能点**同时生成，墙钟≈÷N。**诚实**：此并行只在 Claude Code 成立；Cursor/Codex 等退回串行，不写成产品承诺。
3. **增量只生成改动项**：只生成**新圈/改过**的功能点（走 `anno-ai-queue`），已生成的不重跑；改一处 PRD = 只重生成受影响的那一个 fp，禁重写整篇。
   - 🔧 **改 PRD 先查后改（2026-10-09）**：`node skills/prd/pd.js <prd-data.json> show <功能点>` 定点看某功能点**现有**字段规范 + 7 节用例规则（prd-data 几 MB·禁整份读；list/show/get/find 四命令按需查）→ 看清要改哪一节，再用 `prd-draft` 出骨架 + 填业务 → `/anno-inject` 重生成那**一个** fp（写入走 anno-server·自动重算 md/docx；pd.js 只读不写，直接改 prd-data 会让 md/docx 脱节）。

- ❌ **禁**：机械预生成「字段/业务规则」的实质内容（违反 R-D + 禁臆造，出垃圾）。复制那一下是瞬间，真正的耗时是 AI 写业务内容，砍不掉、只能靠上面三条压到最小。
- 🏛 **三产物分离**（见 `CLAUDE.md §画原型提速铁律`）：① 原型=`assemble --fast`(85ms) · ② PRD=本节 · ③ data_model=`derive-from-prototype`/`emit-all`(确定性·秒级)。**②③ 都不进 ① 生成原型**，各自按需触发、互不拖累。

## 缺失信息处理

关键信息不足时，先提最少必要问题再写正文。优先询问：

1. 目标用户是谁？
2. 要解决的核心问题是什么？
3. 成功指标如何衡量？
4. 本期范围与不做项是什么？
5. 系统视图是否分端、菜单结构、各菜单下功能点清单（按 `菜单路径：功能点1、功能点2` 格式给出）？

## 输出要求

- 默认输出结构化 Markdown。
- 每条需求项必须含：用户故事、业务规则、验收标准。
- 明确区分"本期范围"与"非目标"。
- 系统视图、菜单名、功能点名一律取用户当次输入的真实命名，不套用示例。
- 文档语言要求清晰、易懂、可直接执行；优先短句；术语首次出现需就地解释。**具体分寸见下方「直白写法铁律」。**

### 🔴🔴🔴 适用范围铁律（2026-11-06 用户明令 · 随包 · 任何工具 · 任何用户）

> 用户原话（11-06）：「不管是我使用，还是别的用户安装我的 skill 后，不管是否按照标准的撰写 PRD 模版，还是用户在对话框里根据个人的要求增加的文字内容，你都要统一遵守这个规则和要求。」

本节以下的全部写法和版式规则——中文书面用语、【】和“”、句末用句号、一段一件事的分段、无编号段落首行缩进 2 个字、Word 版式（微软雅黑五号、不倾斜、红字写法）、md 和 Word 始终一致（Word 优先铁律）、字段规范没有字段时写“无。”——**统一适用于以下所有情况，没有例外**：
1. 用户本人使用，或别的用户安装本 skill 后使用（用 Claude Code、Cursor、Codex、OpenClaw 等任何工具）。
2. 按标准 PRD 模板撰写的文档，以及不按标准模板、按用户自己结构撰写的文档（例如《按我的结构》）。
3. 用户在对话框里按个人要求让增加或修改的任何文字，包括新增的章节、段落、表格和说明。

**机器兜底**：`make-doc.ps1` 生成 Word 时，标准模板的 PRD 跑完整检查；不按模板的文档自动跑 `prd-structure-lint.js --writing-only`（只查写法），不通过就报错。缩进、字体等版式由模板和过滤器统一处理，与文档结构无关。

### 🔴🔴 中文书面用语 / 直白写法铁律（2026-11-03 用户明令 · 随包 · 任何工具一样 · PRD、各类文档、原型说明、对话回复都适用）

> 用户原话（11-03）：「我要求你输出的内容全部是中文的书面用语，标准汉语的写法。不允许使用看不懂的简写、大白话、口头禅。以后不要输出 AI 味道太重的这类看不懂、需要让人猜的简写和大白话文档。」

**禁用清单（写完逐项自查，命中即改成标准书面汉语）：**

| 类别 | 禁止的写法（举例） | 应改为 |
|---|---|---|
| 口语词、口头禅 | 就是、其实、说白了、咱们、搞定、弄、啥、咋、去哪儿改、照开、打回来、一眼看出、靠谱、兜底、落到、卡死、多了这张票、号没被占用 | 即、实际上、因此、修改位置、仍需开具、被税局拒绝、直接看出、可靠、保底处理、进入、无法继续、新增这张发票、发票号未被占用 |
| 箭头、斜杠、等号代替句子 | 「超时 → 当 223 → 开票失败」「信息错 → CC-e」「前 8 位相同 = 同一家公司」「被拒 / 查不到」 | 写成完整句子：谁、在什么情况下、做什么、结果是什么 |
| 省略主语和结果的半句 | 「改完回【开票失败】」「隔几分钟重试」 | 「用户修改完成后，回到【开票失败】页签重新提交」 |
| 破折号旁注 | 「已提交税局 —— 这张票已移到开票中」 | 用逗号、分号或另起一句 |
| 模棱两可 | 按情况处理、相关内容、一般会、可能需要、以最新为准、尽快 | 写明具体条件、具体对象、具体时限 |
| AI 腔 | 「一句话：」「← 就是它」、口号式加粗、感叹号、「说人话」、自造的缩略词 | 正常陈述句 |

**标点铁律（2026-11-03 用户明确）：不使用「」。** 系统模块、系统功能（菜单、页面、页签、按钮、功能名）一律用【】，例：【开票失败】【开具CC-e】；状态、类型和枚举值一律用“”，例：发票状态变为“已取消”、发票类型为“货物调拨”；引用界面提示原文整句也用“”。原型文案同样适用。

**总原则（2026-11-06 用户明令）：用户手动在本地改了 Word 或 md，以最新改的那一份为准。**
> 用户原话（11-06）：「如果我手动本地改了 WORD 或者 MD 格式，以最新的为准。」
> 用户一句话总结（11-06）：「如果我手动在本地改了同一个文件的某个格式，举例：我改了 Word 格式，没有改 MD 格式，那么对应的 MD 格式也要一起更新；反之，如果我改了 MD 格式，没有改 Word，那么 Word 格式也一起更新。如果我在 AI 对话里让你改 PRD，那么 MD 和 Word 格式要同步一起更新。」

| 情况 | 怎么做 |
|---|---|
| 用户在本地只改了 Word | 把 Word 的改动同步进 md，不动 Word |
| 用户在本地只改了 md | 用 md 重新生成 Word |
| 用户在 AI 对话里让改 PRD | md 和 Word 同一轮一起改完 |
| 两边都被用户改过 | 合并两边的改动；同一处写得不一样时，列出原文问用户 |

- 动 PRD 之前，先运行 `node skills/prd/qa/docx-guard.js status <docx> <md>` 看上次生成之后谁被改过：
  - 只有 Word 被改过（退出码 3）：以 Word 为准，按下面第一条把 Word 的改动同步进 md，不动 Word。
  - 只有 md 被改过（退出码 10）：以 md 为准，重新生成 Word。
  - 两边都被改过（退出码 4）：把两边的改动合并；同一处两边写得不一样时，列出两边原文，问用户以哪边为准，不许自己猜。
- AI 改 md 时，每次都从磁盘读最新的 md 再改，不许用之前读到的旧内容整份写回，以免冲掉用户刚手动改的内容。

**两个方向，规则不同：**
- **用户改了 Word** → AI 把 Word 的改动同步进 md（文字、分段、换行、红字都照 Word），**不动用户的 Word**。同步后逐段比对 md 生成的 Word 与用户的 Word，差异必须为 0，再记录指纹。
- **用户在对话框里让改** → md 和 Word 同时一起改，同一轮里完成。改之前先检查 Word 有没有被用户改过；改过就先按上一条把 Word 的改动同步进 md，再改、再生成 Word。**只改了 md、Word 没有重新生成，不算做完**；Word 被占用无法生成时，要告诉用户，等 Word 关闭后补生成。

1. **生成前先判断 Word 有没有被用户改过**：每次由 md 生成 Word 后，系统记下这份 Word 的指纹（同目录隐藏文件 `.<Word 文件名>.gen`）。之后 Word 的指纹和记录不同，就是用户改过 Word。没有指纹记录的旧 Word，按文字比对，Word 里有、md 里没有的句子即视为用户的改动。
2. **用户改过 Word 时**：先运行 `node skills/prd/qa/docx-guard.js diff <docx> <md>` 列出差异，把 Word 里的增、删、改逐条同步进 md（包括用户删掉的句子，md 里也删掉）。同步完成后再跑一次 `diff`，差异为 0 时运行 `node skills/prd/qa/docx-guard.js stamp <docx>` 记录指纹。**只同步时不重新生成 Word，用户的 Word 保持原样**；用户在对话框里又提了新改动，才改 md 并用 `make-doc.ps1 -WordSynced` 重新生成。
3. **机器拦截**：`make-doc.ps1` 生成前自动检查，用户改过 Word 时停止生成、不覆盖，并列出差异（退出码 3）。anno-server 自动生成时同样不覆盖，新内容另存为“-新生成(原Word已被修改未覆盖).docx”。
4. **`-WordSynced` 只在 Word 的改动已全部同步进 md 后使用**，不许为了绕过拦截直接加这个参数。

**断句铁律（2026-11-04 用户明令）：一句只讲一件事，讲完用句号断开。**
> 用户原话（11-04）：「这个对吗？没有断句吗？」「整个文档，你全部检查一下，那些没有断句的，全面检查，按中文的书面用语习惯进行更改。」
> 起因：表格里写成「发票状态为“已开票”的都可以开；可以更正地址、商品描述、备注等不影响税额的信息，金额、数量错误不能通过 CC-e 更正」——三件事挤在一句里，用分号、逗号硬连，内容还不全。

1. **不同的意思用句号分开**：条件、规则、例外、结果、原因，各自成句。“可以……”和“不可以……”、“能……”和“不能……”必须分成两句。
2. **分号只用于同类并列**：几项同一性质的内容并列时才用分号（如三种情况各自的处理方式）；不用分号把不同性质的话连成一句。
3. **逗号不能一逗到底**：一句里超过三个逗号，或超过约 60 个字，先检查能否拆成两三句；能拆就拆。
4. **表格单元格同样适用**：单元格里有两件以上的事，用句号分开；有并列多项时写成“1、……；2、……”。
5. **拆句不改意思**：不增删事实、条件、数字；“”内引用的界面原文（提示语、按钮名）保持原样，要改须原型同步修改并先征得用户同意；PRD 标准规范里的固定句式、固定表头不动。
6. **同一条规则只写在一处**：别处需要时写“见本节第 N 条”，不重复写一遍不全的版本。

**句末标点铁律（2026-11-06 用户明令）：按中文书写习惯，一句话表达完一个意思，用句号“。”结束。**
> 用户原话（11-06）：「必须按中文的书写习惯，表达的意思结束后，要用。句号结束。」
> 起因：两份发票 PRD 正文有 379 行句末用“；”，表格里 2000 多个完整句子结尾没有标点。

1. **正文**：一句话或一段话说完，用“。”结束；不用“；”“，”或什么都不写来收尾。列举 1、2、3 时，每一项说完也用“。”。
2. **表格单元格**：单元格里是完整的句子（有条件、动作、结果，常见形式是用逗号或分号连起来的一句或几句），结尾用“。”。
3. **以下内容不加句号**：
   - 标题、加粗的小标签（如“**位置**”）、菜单路径（含 ›）、章节号。
   - 表格里的名称、短语和取值，例如“调拨单（同一家公司不同发票主体之间，仓库调到仓库）”“NF-e 55 销售退票”“是”“无”。
   - 以冒号结尾、后面接列表的引导语。

   - 操作日志示例、数据格式、编码和取值清单。
   - 章节引用清单，例如“4.2.3 第 4 条；4.4 调拨管理章”。
4. **引号里已有句号的不重复加**：例如显示“尚未开票，请在待开票状态下执行【开票】操作。”，句号在引号内，引号外不再加。
5. **不改换行结构**：只改句末那一个标点，不合并或拆分用户已经换好的行。

**一句话：输出的文档和 PRD，全部使用中文书面用语。**

**直白 = 正常的书面中文，把意思讲完整，让没参与讨论的人第一次读就看懂。** 不等于口语化，更不等于简写。

> 用户原话（11-03）：「以前输出的文档，全是那种模棱两可的话。我要的直白写法，是正常的书面话，不是极端大白话、简写的大白话，那样看不懂。」
> 以前的毛病有两种，都要改：
> - **模棱两可**：「按情况处理」「相关内容」「一般会」「可能需要」「以最新为准」——读完不知道到底谁做、做什么、结果怎样。
> - **简写的大白话**：用箭头、斜杠、顿号串成半句话，省掉主语和结果，例如「超时→当223→开票失败」「信息错→CC-e；金额错→回单据」。写的人懂，读的人看不懂。
>
> 正确写法：「提交开票后如果超时没有收到税局结果，系统按税局返回 223 处理，发票进入【开票失败】页签。」

1. **句子写完整、意思写准确**：读完能知道谁、在什么时候、做什么、结果是什么。意思本身清楚的规则照常写，不需要每条都加原因和例子；只有容易误解的规则（例如 CC-e 第二次要把第一次的更正重新写一遍）才补一句原因或一个例子。
2. **不许写成"压缩句"或"模棱两可的话"**：「最新一次生效」「之前的要一起写」「以最新为准」「按情况处理」「相关内容」这种只有写的人自己懂的话，必须展开成完整的句子：谁、在什么时候、要做什么、结果是什么。正文里不用箭头（→）、斜杠（/）代替句子；箭头只用在流程图和"页面 › 页签"这类路径里。
3. **例子要具体**：用真实的字段、单据、数值（「第一次改了收货地址」），不用「某字段」「X」「相关内容」这类空泛说法。
4. **术语第一次出现时就地解释**（例：CC-e（更正函，用于更正不影响税额的信息））；同一个东西全文只用一个叫法。
5. **不许走极端**——直白不等于口语：
   - 不用「就是」「其实」「说白了」「咱们」「搞定」这类口语词，也不用破折号挂一句白话旁注（与 [pm-design 中规中矩铁律](../pm-design/SKILL.md) 一致）；
   - 不为了"好懂"删掉必要的条件、例外、法规依据——条件和依据照写，只是写成完整句子；
   - 界面文案（字段值、按钮、提示语）仍然只写真系统会出现的话；解释放到「？」浮层、【说明】、PRD 正文。
6. **只管句子怎么写，不改 PRD 标准规范**：章节结构、表格格式、固定句式（如取消路径固定句、操作日志说明语、提示消息表头）一律按 [prd-template-structure.mdc](./_rules/prd-template-structure.mdc) 和 annotation-templates，本铁律不得用来改动它们。
7. **自查**：写完读一遍，问自己"一个没参与讨论的业务人员第一次读，能不能看懂要做什么、不做会怎样"。读不懂的句子就展开或补例子；冒出口语词的就改成书面说法。

## 与 pm-design skill 的衔接

- **上游**：[pm-design skill](../pm-design/SKILL.md) 生成 `.html` 原型（含标注层）
- **本 skill**：把原型 HTML 当作字段提取来源（替代传统截图）→ 生成 PRD `.md` + `prd-data.json`
- **数据流**：
  ```
  用户写 1 份 prompt
    ↓
  pm-design 出原型 HTML（默认带标注层，预留 data-annotation 属性）
    ↓
  用户确认
    ↓
  prd skill 出 PRD .md + 同步生成 prd-data.json
    ↓
  pm-design 把 prd-data.json 内联回原型 HTML 的 window.__PRD_DATA__
    ↓
  用户打开 .html → 标注层可用（点 ℹ️ 查看字段规范 / 用例规则）
  ```

- **双向同步**（v1.0 MVP 阶段是只读，v1.x 加编辑能力）：
  - PRD `.md` 与 `prd-data.json` 与原型 HTML 三者**单一数据源**
  - MVP：用户改 `.md` → 让 AI 同步刷新 `prd-data.json` 和原型 HTML
  - v1.x：用户在原型抽屉里编辑字段 → 浏览器导出新 `.md` + `.json`

## 🔁 两种方式生成 PRD + 标注（2026-11-13 用户定·两种并存·必守）

用户原话：“1、我即可以通过点选和圈选来让你根据我的范围生成PRD，2、同时我也可以不用点选和圈选，让你把所有的功能点生成PRD后，你自动生成把PRD里对应的功能都显示字段规范和用例规则。”

| 方式 | 用户做什么 | AI 做什么 |
|---|---|---|
| ① 圈选/点选 | 在原型上圈选或点选范围 | 按圈选范围生成 PRD，走原有 anno-server 注入回路，标注就是用户圈的那个位置 |
| ② 不圈选（整页/整个原型） | 只说“生成 PRD”或“改 PRD” | 写完 PRD（md+Word）后，**自动**把 PRD 里每个写了【字段规范】或【用例规则】的功能点放进原型对应按钮的标注，不用用户圈选 |

两种方式对**任何人、任何安装了本工具包的原型**都适用（用户 11-13：“不管是我用还是用户安装后使用”），不依赖本机路径或某个项目。

方式②的固定做法（每次 PRD 有改动都重跑，不靠用户提醒）：
0. **映射表不手写，先自动生成**：`node skills/prd/auto-anno-map.js <PRD.md> <原型交付件.html> <project-data 去掉 .json>.anno-map.json`——自动在浏览器里逐页、逐页签、逐快捷筛选爬出所有可见按钮，按 PRD 功能点名和所在章节（页面/页签名）自动配对，同名功能自动带上电商、零售等所有出现的页面；同时出 `<输出>.report.txt`，每条标 高/中/低 可信度。AI **必须**逐条复核报告里“中/低/⚠ 请人工确认”的条目（多半是要走业务流程才出现的按钮，如结账后、详情里、弹层里），改好映射再往下走。首次爬约 5～11 分钟；改了 PRD 没改原型时加 `--inventory <上次清单.json>` 复用清单，1～2 秒出映射。实测（发票原型 72 个功能点）自动三项全对 76%，其余靠第 4 步核对补正。
1. 映射表 `<project-data 去掉 .json>.anno-map.json`（放在 project-data 同目录）：每个功能点一行 `{"secs":["章节号"],"pages":["页面id",…],"tab":"选中的页签文字" 或 [多个同时选中],"texts":["按钮文字","兜底如 更多"],"notTab":"可选：这些页签选中时不显示"}`。电商、零售同名功能写在同一行的 pages 里（一个标注两边都显示）。
2. `node skills/prd/prd-to-annotations.js <PRD.md> <anno-map.json> <project-data 去掉 .json>.annotations.json`：把每个功能点的字段规范、用例规则**原文**带进标注（只读 PRD，绝不改 PRD）；PRD 有、映射没有的功能点会列出并退出码 2——**必须补映射，不许漏**。
3. 重建交付件（`rebuild-deliverable.ps1`，装配器自动把 annotations.json 烤进原型）；标注层 1.11.0 起 `pin.anchor` 跟着按钮走：换屏幕宽度、切页签自动对位；按钮看不到（开关关闭、在别的页签）就不显示，不会乱放。
4. 在交付件里用浏览器逐个核对：`node skills/prd/verify-anno-anchors.js <原型交付件.html> [--map <anno-map.json>]`（带 --map 可在重建前先验映射草稿）——每个标注在对应页面、对应页签的按钮上出现（✓），在错误页签不出现；有 ✗ 退出码 1，必须修到 0 个 ✗；⚠ 表示个别子页签本来没有该按钮，复核后可接受。再逐个打开标注，确认字段规范、用例规则都显示出来。
   - PRD 里写“请参考 x.x.x 的目录。不同之处：……”的，标注会自动把被引用那一节的原文接在后面，点开即看全。
   - 只在功能按钮（新增、编辑、删除、开票、导出、导入、查询……）上放标注，页面本身不放（用户 11-13 明令）。
5'. 方式①（圈选/点选）照旧可用：圈选后点【复制已圈功能】（清单带归属目录、身份、状态）→ 粘给 AI 按范围生成 PRD → 自动注入到圈选位置。两种方式产生的标注可以共存，PRD 标注更新时只替换 PRD 生成的那一批，用户自己圈选的保留。
4'. 页面级写法也支持：一个页面的【字段规范】【用例规则】两节下面再按功能分小节（如 5.1.6.1 新增发票主体 / 5.1.7.1 新增发票主体），两边小节名和顺序一致，工具会把同名小节配成一个功能点，各出一个标注挂到各自按钮上（映射表 secs 写用例规则那边的章节号）。
5. 只给 PRD 里有字段规范或用例规则的功能点放标注；没写的功能不放（用户 11-13：“如果原型的功能点，在PRD里没有字段规范和用例规则，就不用显示”）。
6. PRD 更新后标注自动整套替换（文件里烤的 PRD 标注带内容签名，浏览器里旧的 PRD 标注会被替换；用户自己圈选的标注保留）。

## 📐 标准模板 + 个性化结构 两种生成方式（2026-11-13 用户明令·必守）

用户原话：“我使用和用户安装skill后，用户让你生成的PRD是一个标准版本格式的，但用户在对话框如果让你按对方的要求生成PRD的相关章节，也是可以的，这个不冲突，你生成PRD，要同时支持，按标准模版生成和用户提个性化要求生成……但用户提个性化生成的PRD，其流程图、原型、字段规范、用例规则，这些章节的标准内容，都必须是和撰写PRD skill的标准模版章节是一样的。”

1. **默认**：用户没提结构要求 → 按标准模板（`_rules/prd-template-structure.mdc`）生成。
2. **个性化**：用户在对话框指定章节结构（如“按我的结构”“业务分析报告写法”“只写某几章”）→ 照用户的结构生成，章节名、顺序、层级听用户的。
3. **不管哪种结构，四个小节的写法必须和标准模板完全一样**：
   - 【流程图】：mermaid 源码（转 Word 时渲染成图）或图片，没有写“无。”；
   - 【原型】：放原型截图（自动截图），图下说明照标准写法；
   - 【字段规范】：五列固定表头 | 字段名称 | 类型 | 是否必填/必选 | 默认值 | 约束规则 |，没有字段写“无。”，默认值和占位按 §3.1.5；
   - 【用例规则】：• 前置条件 / 操作流程 / 后置条件 / 校验规则 / 提示消息 / 消息通知 / 操作日志 七节齐全且按顺序，提示消息、消息通知、操作日志用标准表头和固定说明语；
   - 写“请参考 x.x.x 的目录。不同之处：……”引用别处的算合规（标注里会自动把被引用那节原文接在后面）。
4. **机器把关**：`qa/prd-structure-lint.js` 的 STD 规则对任何结构的 PRD 都查这四节（`--writing-only` 个性化文档也查），不合规判红；H1 规则查“带章节号的加粗小节”（必须写成标题，Word 左侧目录才显示）。
5. 用户当前在用、在改、推 GitHub 的是哪一份 PRD，以用户说的为准（发票项目 11-13：修订版《ERP／WMS／零售系统-发票管理系统-修订版：2026-11-11》；标准版那份先不管，能顺手同步可以同步）。

## 🌐 改完自动更新到网上（用户约定后执行·2026-11-13·通用）

1. **触发条件**：用户说过“以后 PRD 和原型改完，自动更新到网上”这类话，并且已经配置好发布仓库（一个本地 git 仓库，已开启 GitHub Pages 或其它静态托管，本机已登录、能推送）。两个条件缺一个就不自动推送，只告诉用户还差哪一步。
2. **每次改完 PRD**（Markdown 和 Word 都已更新、检查通过后）：运行 `node skills/prd/publish-prd-html.js <PRD.md> <发布仓库里的网页目录> [标题]`，生成只读在线网页（`index.html` 和 `img/`），然后在发布仓库里 `git add`、`git commit`、`git push`。
3. **推送后核对**：约 1 分钟后打开线上网址，确认目录、流程图、图片和红字都完整，再告诉用户“已更新到网上”并给出网址。
4. **路径不写进工具包**：发布仓库的位置、网页目录和网址由用户告诉 AI，记在本机的记忆或项目说明里；本节和任何随包文件都不写个人路径、公司名或客户名。
5. **原型只读版**：见 pm-design SKILL.md 的同名一节。用户只约定了其中一项（只更新 PRD 或只更新原型）时，只推送那一项。
6. **推送失败**（未登录、网络问题、冲突）：停下来告诉用户原因，不反复重试。
