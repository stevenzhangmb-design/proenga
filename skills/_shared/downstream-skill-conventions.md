# 下游文档技能公共约定（单一真理源）

> 🏛 **定位**：dev-prompts / tech-design / test-case / product-pitch 四个下游技能的**公共约定**集中在此一处定义，各技能只**引用**本文件，禁止各自再抄一份（防漂移）。
> 各技能特有内容（模板、章节结构、要素清单）仍留在各自 SKILL.md / template.md，本文件只统一**输出约定 / 同步 SOP / 数据契约指针 / 跨技能生成顺序**。

---

## 1. 输出约定（统一）

- **输出目录**：交付文件写入**用户为本次任务选定的输出目录**（默认 `./archive/`，但**每次任务都先与用户确认目录**——遵循既有铁律「输出目录以使用者为准」，禁止写死个人绝对路径）。
- **文件命名**：`<文档类型前缀>-<模块/系统名>-<YYYY-MM-DD>.md`
  - 各技能保留自己的**文档类型前缀**：dev-prompts=`研发提示词`、tech-design=`技术概要设计`、test-case=`测试用例`、product-pitch=`产品方案`。
- **必同步出 .docx**：每个 `.md` 交付物都必须用 pandoc 同步生成对应 `.docx`（遵循既有铁律「任何 .md 必须同步生成 .docx」）；pandoc 不可用时静默跳过 `.docx`，但 `.md` 必出。

---

## 2. 统一同步 SOP（解决各技能矛盾的真理源）

当原型 / PRD（`prd-data.json`）变更时，受影响的下游文档按以下规则同步：

> **默认【整篇重新生成】**以保证与最新数据源完全一致（避免增量改时遗漏跨节依赖）。
> **唯一例外：test-case** —— 因测试用例按功能点逐条编号（TC-xxx），可【**增量增删变更的用例**】而非全文重写。

**理由**：研发提示词 / 技术设计 / 售前方案存在大量跨章节依赖（一个字段变更牵动建表、接口、状态机、功能亮点等多处），整篇重生才能保证一致；测试用例以「功能点→编号用例」一一对应、耦合度低，增量增删即可保证准确且省成本。

无论整篇重生还是增量，**都必须在文档头追加变更日志**，列出本次变更点。

---

## 3. 数据契约指针（prd-data.json 字段语义真理源）

- `../pm-design/prd-data-schema.md` 是 `prd-data.json` 所有字段的**唯一 schema 真理源**。
- 各技能 SKILL.md 里的「与 prd-data.json 的映射规则」表，**只负责把 schema 字段 → 本技能的章节/产出**做映射，**禁止重新定义字段语义**（字段含义、必填、约束等一律以 schema 为准）。

---

## 4. 跨技能生成顺序（集中登记）

下游文档的生成顺序 / 依赖关系：

1. **tech-design** ← 原型 + PRD 确认后即可生成（dev-prompts 的内容源之一）。
2. **dev-prompts** ← 依赖 tech-design 的输出（技术设计越详细，提示词越扎实）。
3. **test-case** ← 原型 + PRD 确认后即可生成。
4. **user-manual** ← 业务理解层，需先于售前方案。
5. **product-pitch** ← **必须在 user-manual 之后或同时**，不可先于它（操作手册的业务术语/场景是售前方案业务对象命名的来源）。

> 以上 1–3 之间无强制先后；硬约束只有两条：dev-prompts 依赖 tech-design 内容源；product-pitch 不得先于 user-manual。
