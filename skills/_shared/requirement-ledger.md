# 需求清单规范（防遗忘 · 防漏做）

> 适用：画原型、改原型、写 PRD 等所有「用户提要求 → AI 改东西」的工作。任何 AI 工具、任何用户一样执行。
> 为什么：对话一长，早期内容会被压缩成摘要，细节就丢了。要求只靠 AI「记住」一定会漏。**要求必须落成文件，不落文件 = 没收到。**

## 1. 清单放在哪

- 每个原型（或每个项目）目录下一份 **`原型改动清单.md`**。模板：[`templates/原型改动清单.md`](templates/原型改动清单.md)。
- 开始改某个原型时：先找这份清单，没有就用模板建一份。
- 把清单的**绝对路径**登记到仓库根的 `.claude/ledgers.txt`（每行一个；本机专用，已 gitignore）。钩子靠这个登记表找清单。

## 2. 怎么记

| 列 | 写什么 |
|---|---|
| # | 流水号，只增不改 |
| 日期 | 提出日期 |
| 你的要求 | **用户原话或原意**，一条消息里有几件事就拆成几行，不许合并 |
| 状态 | 只有四种，见下 |
| 证据 / 说明 | 「已做」写**在交付件里怎么验过的**；「等你定」写**我的建议**；「暂缓」写用户原因 |

**四种状态**

| 状态 | 含义 | 规矩 |
|---|---|---|
| `本轮·待做` | 这一轮要做完 | 还有这一项就**不能收工** |
| `已做` | 做完且验过 | 证据必须具体（验了什么、结果是什么），不许只写"已修改" |
| `等你定` | 真的需要用户拍板 | 必须附建议；用户说过"不要让我选择"的，**直接按建议做完改成已做** |
| `暂缓` | 用户说先不做 | 写明是用户说的 |

**给建议的铁律（用户 2026-11-07 明令·回复问题时必守）**：
1. 每条建议都要写成“改哪里 + 改成什么”：走到哪个模块 › 页面 › 页签或弹窗 › 字段或按钮，原来是什么、改成什么（界面原文直接给出）；原型和 PRD 各改哪几处也要写清。
2. 不许写“可以考虑”“视情况而定”“A 或 B 都可以”这类落不了地的话；有备选时必须给推荐，并说明为什么选它。
3. 自己拿不准的（业务规则、税务、竞品做法），先深度研究竞品系统和当地税法（如巴西 SEFAZ 法规、州税局答复），研究完再给建议，并标注证据等级；没研究清楚的不许给建议。

## 3. 什么时候读、什么时候对

1. **收到新消息**：先记清单，再动手。
2. **每轮开工**：先读清单，看有没有遗留的 `本轮·待做`。
3. **说"做完了"之前**：逐条对一遍，回复里列出本轮做了哪几条、还剩哪几条。
4. **顺带发现的问题**：也记一行（标注"顺带发现"），做或不做都要有状态。

### 🏛 铁律：按用户提的顺序做，一件不漏（2026-10-27 用户明令）
- 用户在对话框里陆续提的要求（包括做事过程中插进来的新消息），**按提出的先后顺序逐件做**，不许挑容易的先做、不许跳过、不许并成一句糊过去。
- **只有用户明确说「停 / 中断 / 先别做 / 先做 X」才改顺序**；其余新消息一律排到队尾，不打断手上这件。
- 每做完一件，在回复里写清楚：改了什么、在交付件里怎么验过；没做完的照原顺序列出来。
- 例外只有一种：后一件是前一件的前提（不先做就做不了），要先说明再调整。

### 🏛 铁律：防“说了却漏做”三条（2026-11-09 用户明令「改成机器强制，不靠自觉」）
事故：用户早先说“门店预订单恢复成收银订单下的页签”，后来暂缓；再提同一件事时还附了真系统截图，AI 没翻旧条目，按字面只改了门店预订单单独那一页，自测只验了自己理解的样子，就报“做完了”。
1. **关联旧条目**：每收到一条要求，先在清单里按页面名、按钮名、【】里的名字搜「暂缓 / 等你定」的旧条目。是同一件事的，新条目写「关联第 X 条」，旧要求一起做，回复第一句告诉用户。
2. **原话 + 验收标准**：需求一栏照抄用户原话，不改写成自己的话。消息带截图的，写「（有截图）」+「验收：对照截图的哪一处」。做完在交付件里截同一位置和用户截图对比，证据一栏写「截图对比：……一致」。
3. **有歧义先停**：只要回复里写了“我的理解是……”，这一条就是「等你定」，等用户回复才动手；不许同一轮边复述理解边改文件。

## 4. 机器兜底（Claude Code 自动；其它工具按本规范自觉执行）

| 钩子 | 脚本 | 作用 |
|---|---|---|
| UserPromptSubmit | `skills/_shared/qa/_userprompt-ledger-hook.js` | 每收到一条消息，提醒 AI 先记清单；**自动列出和这条消息相关的「暂缓/等你定」旧条目**（按 3～8 字的词和【】名字匹配）；**消息带截图时要求写「（有截图）」+ 验收标准**；记下本轮开始时各条目状态（`.claude/ledger-turn.json`，本机专用） |
| Stop | `skills/_shared/qa/_stop-ledger-check.js` | 清单里还有 `本轮·待做` 时拦住收工，列出条目；**清单同目录有内容不为空的 `*.added-pending.txt`（用户没批准的新增项）也拦**；**本轮才改成「已做」且写了「（有截图）」的条目，证据里没有「截图对比」也拦**；**本轮回复写了“我的理解是/我理解为/我理解的“……”又改了文件（清单除外）也拦**；同一次收工第二次触发只提示不拦（防死循环） |

**新增项对比（2026-10-29 用户铁律「没让做的一个都不许加」）**：`skills/pm-design/qa/added-structure-audit.js <project-data.json>` 把源数据和【用户上次认可的基线】`<名>.audit-base.json` 比，只列**新增**的结构（新页面/弹窗/详情/板块/页签/字段/列/按钮/示例单/示例行；改文字不算），写进 `<名>.added-pending.txt`。`rebuild-deliverable.ps1` 每次重建完自动跑。有新增 → 必须在回复里逐条列给用户；用户点头后跑同一命令加 `--accept`（当前数据记为新基线、清空待批准）；用户不同意 → 撤回。第一次运行没有基线时以当前数据建基线。

两个钩子都随 `.claude/settings.json.example` 发。**安装时把它复制成 `.claude/settings.json` 才会生效**（见 `INSTALL.md`）。没登记清单的项目，两个钩子都静默，不打扰。

## 5. 自检（装好后验证）

在对话里提一个要求 → AI 应该**先把它写进清单**再动手；做完回复里应列出清单状态。没出现 = 钩子没生效（检查 `.claude/settings.json` 是否存在、是否登记了清单）。
